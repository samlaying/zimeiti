## 一、Git 不是"线"，是 DAG

### 什么是 DAG？

DAG 的全称是 **Directed Acyclic Graph**，中文叫"有向无环图"。

听起来很吓人，我们拆开来看：

| 术语 | 含义 | 通俗解释 |
|------|------|----------|
| **有向（Directed）** | 有方向 | 每次提交都指向上一次提交，箭头只朝一个方向走 |
| **无环（Acyclic）** | 没有环路 | 不会绕回之前的节点，历史不会"倒流" |
| **图（Graph）** | 网状结构 | 不是一条直线，而是一张可以分叉、合并的网络 |

### 为什么不是"线"？

很多人以为 Git 的历史是一条直线：

```
A → B → C → D
```

但实际上，当多人协作或使用分支时，历史会分叉和合并，变成一张**网络图**：

```
      C → D
     ↗      
A → B       
     ↘      
      E → F
```

**A** 是起点，**B** 之后分出了两条路径（两个分支），分别各自前进。这就是"DAG"的意思——方向向前、没有环、呈网状。

---

## 二、分支 = 指向 commit 的标签指针

### 什么是 commit？

**commit（提交）** 是 Git 中保存项目某个时间点状态的"快照"。就像你玩游戏时的"存档"，每个 commit 记录了那一刻项目的完整状态。

### 分支到底是什么？

这是理解 Git 最关键的一点：

> **分支不是一条线，不是一个文件夹，它仅仅是一个指向某个 commit 的"小标签"。**

举个例子，假设当前有三个 commit：

```
commit A ← commit B ← commit C
```

现在有一个叫 `开发分支` 的分支，它指向 commit C：

```
commit A ← commit B ← commit C
                              ↑
                          开发分支
```

**"开发分支"本身没有任何复杂的东西，它就是一个写着"C"的指针，告诉你"这个分支的最新位置在 commit C"。**

当你在 `开发分支` 上做了一次新的提交（commit D），Git 会做两件事：

1. 创建新的 commit D，它的父节点指向 commit C
2. 把 `开发分支` 这个标签指针从 C **移动到 D**

```
commit A ← commit B ← commit C ← commit D
                                        ↑
                                    开发分支
```

就这么简单——**分支就是一个会自动移动的指针**。

---

## 三、HEAD = 当前指针

### HEAD 是什么？

**HEAD** 是 Git 中的一个特殊指针，它告诉你"你现在在哪里"。

> **HEAD 指向当前所在的分支，当前分支再指向具体的 commit。**

这是一种**两层间接指向**的关系：

```
HEAD → 开发分支 → commit C
```

用一个生活比喻：

- **commit** = 你站在某个具体的位置（比如"家里"）
- **开发分支** = 你的导航目的地标签（比如"公司路线"）
- **HEAD** = 你的眼睛——你正在看哪个导航路线

### 为什么要这样设计？

因为你可以有很多分支（很多条路线），但你**同一时刻只能在一个分支上工作**。HEAD 就是告诉 Git："我现在在 `开发分支` 上，而 `开发分支` 目前在 commit C 的位置。"

当你切换分支（`git checkout` 或 `git switch`）时，实际上就是让 **HEAD 指向另一个分支**。

```
切换前：HEAD → 开发分支 → commit C
切换后：HEAD → 主分支   → commit A
```

---

## 四、工作区 / 暂存区 / 仓库

Git 把你的文件管理分成了**三个区域**，每个区域有不同的职责。理解这三者是使用 Git 的基本功。

```
  工作区          暂存区           仓库
┌─────────┐    ┌─────────┐    ┌─────────┐
│         │    │         │    │         │
│ 编辑文件 │──→│ 准备提交 │──→│ 保存所有 │
│  的地方  │    │  的快照  │    │ 提交历史 │
│         │    │         │    │         │
└─────────┘    └─────────┘    └─────────┘
   (git add)     (git commit)
```

### 4.1 工作区（Working Directory）

- **是什么**：你能直接看到的项目文件夹，你平时写代码、改文件的地方
- **比喻**：就像你的书桌，上面摊着各种文件，你可以随意翻看和修改

### 4.2 暂存区（Staging Area）

- **是什么**：一个"准备区"，你把想要在下一次提交中保存的改动放进来
- **比喻**：就像一个"打包台"。你从书桌上（工作区）挑出这次要寄走的文件，放在打包台上整理好
- **操作命令**：`git add 文件名` —— 把工作区的改动放入暂存区

### 4.3 仓库（Repository）

- **是什么**：Git 真正保存所有历史记录的地方，所有的 commit 都存在这里
- **比喻**：就像一个"档案室"，每次你打包好文件（暂存区），就存一份永久的档案（commit）
- **操作命令**：`git commit -m "说明"` —— 把暂存区的内容创建为一个新的 commit

### 三者的完整工作流程

以一个实际场景为例：

| 步骤 | 你在做什么 | 对应的区域变化 |
|------|-----------|--------------|
| 1. 写代码 | 在 `index.html` 里写了一个标题 | 只影响**工作区** |
| 2. `git add index.html` | 告诉 Git："这个改动我确定要保存" | 改动进入**暂存区** |
| 3. `git commit -m "添加标题"` | 正式存档 | 暂存区的内容变为一个 **commit**，存入**仓库** |
| 4. 继续写代码 | 又改了 CSS 样式 | 新改动只在**工作区**，不影响刚才的 commit |

---

## 五、整体关系图

把以上所有概念串在一起：

```
┌─────────────────────────────────────────────────┐
│                    Git 全局视图                    │
│                                                   │
│   工作区          暂存区          仓库（.git）       │
│  ┌───────┐     ┌───────┐     ┌───────────────┐   │
│  │你的文件│ ──→ │待提交区│ ──→ │               │   │
│  └───────┘     └───────┘     │  A ← B ← C    │   │
│   git add       git commit   │        ↑       │   │
│                              │    开发分支     │   │
│                              │        ↑       │   │
│                              │      HEAD      │   │
│                              │               │   │
│                              └───────────────┘   │
└─────────────────────────────────────────────────┘
```

---

## 六、一张图总结所有重点

| 概念 | 一句话理解 |
|------|-----------|
| **DAG** | Git 的历史是一张有方向、不会回环的网状图，不是简单的直线 |
| **commit** | 项目某一时刻的完整存档 |
| **分支** | 只是一个指向某个 commit 的指针标签，会随新提交自动前移 |
| **HEAD** | 指向你当前所在的分支，告诉你"我现在在哪" |
| **工作区** | 你看到和编辑文件的地方 |
| **暂存区** | 你挑选出来、准备下次提交的改动集合 |
| **仓库** | 存放所有 commit 历史的档案室 |


**记住这个口诀：改文件在工作区，选文件进暂存区，存文件到仓库。HEAD 看着分支，分支指着 commit，commit 串成 DAG。**

# Git HEAD、本地分支与远程分支 —— 零基础详细讲解

---

## 一、先搞清楚"仓库"是什么

你可以把 Git 仓库想象成一个**快递仓库**：

- **本地仓库**：就在你自己的电脑里，只有你能直接操作。
- **远程仓库**：放在服务器上（比如 GitHub、GitLab），所有协作者都能访问。

---

## 二、什么是"提交"（Commit）

每一次"提交"就像给项目拍了一张**快照**，记录下此刻所有文件的状态。

```
提交A --- 提交B --- 提交C --- 提交D (最新)
```

这些提交像一串珠子，**按时间顺序连在一起**，形成一条链。

---

## 三、什么是"分支"（Branch）

分支就是**一个可以移动的标签**，贴在某一个提交上面，用来标记"这条开发线路现在走到哪了"。

### 1. 本地分支（如 `main`）

- 保存在**你自己的电脑**上。
- 当你做了新的提交，本地分支会**自动向前移动**，指向最新的提交。
- 图片中用**绿色边框**标注的，就是当前正在使用的本地分支。

### 2. 远程分支（如 `origin/main`）

- 保存在**远程服务器**上。
- 它代表的是"服务器上大家公认的那个版本走到哪了"。
- 图片中用**蓝色边框**标注的，就是当前正在使用的远程分支。

> **类比**：本地分支是你自己笔记本上记的笔记，远程分支是贴在公告栏上让大家看的笔记。

---

## 四、什么是 HEAD

HEAD 是 Git 中一个**特别重要的指针**，你可以理解为：

> **HEAD = 你现在站在哪里（当前所在的提交位置）**

### 情况一：正常的 HEAD（Attached HEAD）

正常情况下，HEAD **挂在某个本地分支上**。

```
HEAD --> main分支 --> 提交D
```

这意味着：你现在在 `main` 分支上，位于提交 D。

此时你做一次新的提交 E：
- 提交 E 会被创建出来。
- `main` 分支会**自动往前移**到提交 E。
- HEAD 继续跟着 `main` 走。

**一切井然有序。**

---

### 情况二：分离的 HEAD（Detached HEAD）⚠️

图片中用**橙色边框**特别标注了这个状态，说明它很重要、容易出问题。

所谓"分离的 HEAD"，就是 **HEAD 没有指向任何分支，而是直接指向了一个具体的提交**。

```
HEAD --> 提交B（但不经过任何分支）
main  --> 提交D
```

**怎么进入这个状态的？** 比如你执行了：
```bash
git checkout 提交B的哈希值
```

**危险在哪里？**

- 如果你在 Detached HEAD 状态下做了一个新提交 F，这个提交 F **不属于任何分支**。
- 当你切换回 `main` 分支后，提交 F 就成了"孤儿"——没有任何分支指向它。
- Git 的垃圾回收机制最终会**把提交 F 清除掉**，你的工作就**丢失了**。

> **类比**：正常 HEAD 就像你走在一条有名字的路上（main 路），走过的每一步都有记录。Detached HEAD 就像你离开了所有道路，走进了荒野——你走的脚印没有人记录，很快就会被风吹没。

---

## 五、推送（Push）—— 本地与远程的同步

当你在本地完成了工作（有了新的提交），需要把成果"推"到远程仓库，让其他人也能看到，这就是 `git push`。

| 状态 | 本地分支 main | 远程分支 origin/main | 是否同步 |
|------|-------------|---------------------|---------|
| 推送前 | 指向提交 D | 指向提交 C | **不同步**，远程落后 |
| 推送后 | 指向提交 D | 指向提交 D | **同步**，指向相同提交 |

推送之后，本地分支和远程分支指向**同一个提交**，大家看到的就是同一版本。

---

## 六、总结对照表

| 概念 | 存放位置 | 通俗理解 | 图示标记 |
|------|---------|---------|---------|
| 本地分支（如 `main`） | 你自己电脑 | 你手里的工作进度条 | 绿色边框 |
| 远程分支（如 `origin/main`） | 远程服务器 | 大家共享的公告进度条 | 蓝色边框 |
| HEAD（正常） | 本地 | "我此刻在哪个分支上" | 跟随某个分支 |
| HEAD（Detached） | 本地 | "我脱离了分支，直接站在某个提交上" | 橙色边框 |
| Push（推送） | 本地 → 远程 | 把我的进度同步到公告栏 | — |

---

## 七、给小白的三条安全建议

1. **随时关注 HEAD 状态**：如果 Git 提示你 "You are in detached HEAD state"，要立刻警惕。
2. **在 Detached HEAD 下不要提交代码**：如果一定要提交，先创建一个新分支来保存它。
3. **养成经常 push 的习惯**：本地的成果推送到远程，相当于多了一份备份，不怕电脑出问题。

# 3 Git Merge 详细讲义：保留合并关系
![[已生成图像 3.png]]




## 一、什么是 Git Merge？

在日常开发中，我们经常需要在不同的分支上工作。比如你有一个**主分支（main）**，它是项目的"正式版本"；同时你创建了一个**功能分支（feature）**，用来开发某个新功能。

当新功能开发完成后，你需要把 feature 分支上的工作成果**合并**回 main 分支。`git merge` 就是完成这个"合并"操作的命令。

**一句话总结：git merge 就是把一个分支的内容合并到另一个分支上。**

---

## 二、合并前的状态（看图理解）

合并前，两个分支各自独立发展：

```
○ main 分支      ← 主分支，项目正式代码
○ feature 分支   ← 功能分支，正在开发新功能
```

可以想象成：两条分叉的道路，各自往前走了一段。

---

## 三、合并操作

有两种写法，效果类似：

```bash
git merge feature
```

或者加上 `--no-ff` 参数：

```bash
git merge --no-ff feature
```

> **小白科普：** `--no-ff` 的意思是 "no fast-forward"（不要快进）。加了这个参数后，**无论什么情况**都会生成一个合并提交记录，确保合并历史清晰可查。

---

## 四、合并后的状态（看图理解）

合并后，两个分支汇合在一起，并**产生一个新的"合并提交"**：

```
○ main 分支
○ feature 分支
○ merge commit (合并提交)  ← 新生成的，记录了这次合并
```

---

## 五、Merge 的三大特点（重点）

### 特点一：产生 merge commit

- 合并时会**自动生成一个新的提交**，叫做"合并提交"（merge commit）
- 这个提交的作用：**记录两条分支在哪里汇合的**
- 相当于一个"合并的里程碑"，标记了"从这一刻起，两条分支合为一体"

### 特点二：不改写历史

- 合并后，**原有的提交记录全部保留**，一个不少
- feature 分支上的每一次提交都还在，不会消失
- 这意味着：**安全、可追溯**
- 任何时候你都可以回溯查看：这个功能是分几次提交完成的、每次改了什么

### 特点三：分支图更完整但可能复杂

- **好处：** 完整展示了整个开发脉络——谁在哪个分支上、做了什么、什么时候合并的，一目了然
- **缺点：** 当项目分支很多的时候，图形可能会变得**错综复杂**，不太容易阅读

---

## 六、打个比方帮你理解

把 Git 项目想象成一本书的写作过程：

| Git 概念 | 比喻 |
|---------|------|
| main 分支 | 正式出版的书稿 |
| feature 分支 | 作者在单独编辑的一章草稿 |
| merge | 把草稿内容正式合并进书稿 |
| merge commit | 在书稿上盖一个章："第X章已于X月X日合并" |
| 保留历史 | 草稿的每一页修改记录都还在，随时可以查阅 |

---

## 七、总结

| 项目 | 说明 |
|------|------|
| **命令** | `git merge feature` 或 `git merge --no-ff feature` |
| **会产生什么** | 一个新的合并提交（merge commit） |
| **历史记录** | 完整保留，不改写 |
| **优点** | 安全、可追溯、开发脉络完整 |
| **缺点** | 分支多了之后图形可能比较复杂 |

> **一句话记住 Merge：** 它是 Git 中最"安全"的合并方式——所有历史都保留，合并不留遗憾，随时可以追溯。


# 4 Git Rebase 详细讲解讲义：复制并嫁接提交
![[已生成图像 4.png]]





## 一、Rebase 是什么？——用一个生活比喻理解它

想象你和朋友同时在写同一本书：

- 你在写**第5章**（你的分支）
- 朋友在写**第4章的修订版**（main 分支的最新提交）

现在你想把你的第5章放到朋友修订版之后。你有两个选择：

1. **Merge（合并）**：在书的目录里加一个"合并说明页"，表示"从这里分叉，又从这里合回来了"。这就产生了一个**合并节点**。
2. **Rebase（变基）**：把你写的第5章**撕下来，重新抄写一份**，放到朋友修订版之后。书看起来就像从来没有人分叉过一样——**干干净净，一条直线**。

---

## 二、Rebase 的三个核心特点

根据参考内容，Rebase 有三个关键特性：

### 特点 1：不产生合并节点

> 内容原文："不产生合并节点"

- 用 `merge` 合并分支时，会生成一个特殊的"合并提交"（merge commit），它有**两个父节点**，历史图上会出现分叉再汇合的形状。
- 用 `rebase` 时，**不会**产生这种合并节点。历史看起来就像一条笔直的线。

**对比图示：**

```
Merge 的历史（有分叉和合并节点）：

      C---D---E  (你的分支)
     /         \
A---B-----------M  ← 合并节点 M（有两个父节点）


Rebase 的历史（线性，无分叉）：

A---B---C'---D'---E'  ← 看起来像一条直线，一切都在 main 之后
```

### 特点 2：保持线性历史

> 内容原文："保持线性历史"

- 所有提交像**珠子一样串成一条线**，没有分叉，没有合并。
- 这让项目历史更**清晰、易读**，查看日志时一目了然。

### 特点 3：改写历史——哈希会变

> 内容原文："改写历史：哈希会变，D、E 会变成新的 D'、E'"

这是 **Rebase 最重要、也最需要注意的一点**。

- Git 中每个提交都有一个唯一的 **哈希值**（类似身份证号），比如 D 的哈希是 `a1b2c3d`。
- Rebase 的本质是"**复制**"提交，然后"**重放**"到新的位置。
- 复制出来的提交虽然内容相同，但因为**位置变了**（父节点变了），所以 Git 会生成**全新的哈希值**。
- 原来的 D 和 E 被替换为 D' 和 E'——它们是**新的提交**，不是原来的那两个。

**用比喻说：** 你把作文从作业本上撕下来，重新抄了一遍放在新位置。内容一样，但这是"新的一份"，不是原来的那一张纸了。

---

## 三、Rebase 的执行过程（逐步拆解）

假设当前场景如下：

```
main 分支：    A --- B --- F
                        \
你的分支：              C --- D --- E
```

你想把你的提交（C、D、E）放到 main 最新的 F 之后。

执行 `git rebase main` 后：

```
第一步：先把你的分支"摘下来"
main 分支：    A --- B --- F
                        \
                         C --- D --- E  （原来的，即将被废弃）

第二步：在 F 后面重新"粘贴"一份
main 分支：    A --- B --- F --- C' --- D' --- E'
```

关键过程：
1. **复制**：把 C、D、E 的内容复制一份
2. **重放（replay）**：把复制品依次放到 F 的后面
3. **生成新哈希**：复制品变成 C'、D'、E'，哈希值全部改变
4. **指针移动**：你的分支指针指向 E'

这就是内容所说的："Rebase 会把当前分支上的**复制**一份，并**重放**到目标分支（main）最新提交之后，形成新的**线性历史**。"

---

## 四、推送时的注意事项

> 内容原文："推送需 force-with-lease，避免覆盖他人提交"

### 为什么不能直接 `git push`？

因为 Rebase **改写了历史**（D 和 E 变成了 D' 和 E'），远程仓库还认识的是旧的 D 和 E，你本地已经没有 D 和 E 了，所以普通的 `git push` 会被拒绝。

### 两种推送方式对比

| 命令 | 行为 | 风险 |
|------|------|------|
| `git push --force` | 强制推送，直接覆盖远程 | **危险**：如果别人在旧历史基础上提交了新内容，会被你的强制推送**覆盖掉** |
| `git push --force-with-lease` | 带"租约"的强制推送 | **安全**：Git 会先检查远程分支是否和你上次拉取时一致，如果有人提交了新东西，推送会被拒绝 |

**一句话总结：** 用 `--force-with-lease` 是为了避免你在不知情的情况下，把别人的提交给覆盖掉了。这是一种**防呆机制**。

---

## 五、小白常见疑问

### Q1：Rebase 和 Merge 到底该用哪个？

- **Merge**：保留完整历史，适合公共分支，但历史可能杂乱
- **Rebase**：历史干净线性，适合个人分支在合并前整理提交记录

### Q2：Rebase 会丢失原来的提交吗？

原来的 D、E 在被替换为 D'、E' 后，如果没有其他引用指向它们，Git 会在垃圾回收时清理掉它们。但短期内还可以通过 `git reflog` 找回来。

### Q3：什么情况下绝对不能 Rebase？

**如果别人已经基于你的旧提交在工作，就不要 Rebase。** 因为 Rebase 会改变哈希，别人的代码基础就"消失"了，会导致严重的协作混乱。这也正是为什么参考内容强调要"避免覆盖他人提交"。

---

## 六、总结速记表

| 要点 | 内容 |
|------|------|
| Rebase 是什么 | 复制当前分支的提交，重放到目标分支最新位置之后 |
| 是否产生合并节点 | **不产生** |
| 历史形状 | **线性**，一条直线 |
| 是否改写历史 | **是**，新提交获得新的哈希值 |
| 原始提交会怎样 | 变为新的副本（如 D→D'，E→E'），原提交可能被回收 |
| 推送命令 | 使用 `--force-with-lease`，而非 `--force` |
| 核心风险 | 改写历史后可能覆盖他人的提交 |


# 05 Git Squash Merge 详细讲义：把一串提交压成一个
![[已生成图像 5.png]]

## 一、先用一句话理解 Squash Merge

**Squash Merge** 可以翻译成"压缩合并"。

它做的事情是：

> 把功能分支上的很多个提交，压缩成主分支上的一个新提交。

也就是说，功能分支可能经历了很多小步骤：

```bash
fix typo
add button
adjust style
fix bug
update docs
```

但合并到 `main` 之后，只留下一个干净的提交：

```bash
完成登录页面功能
```

这就是图片里最核心的意思：**feature 分支上有很多节点，但进入 main 后只变成一个 squashed commit。**

---

## 二、为什么需要压缩？

小白刚开始学 Git 时，常常会有一个误区：以为提交越多越专业。

其实不是。

在自己开发时，小步提交很好，因为它能帮你随时保存进度。但当功能要进入主分支时，维护者更关心的是：

- 这个功能最终做了什么
- 是否对应一个完整需求
- 以后查历史时能不能快速看懂

如果主分支上充满下面这种提交：

```bash
改一下
再改一下
修复
试试
终于好了
```

以后团队查历史会非常痛苦。

Squash Merge 的价值就在这里：**开发过程可以细碎，主分支历史要清爽。**

---

## 三、Squash Merge 前后的图形变化

### 3.1 合并前

假设 `main` 分支是正式路线，`feature` 分支是你开发新功能的路线：

```bash
main:     A --- B
                \
feature:         C --- D --- E
```

这里的 C、D、E 可能分别是：

| 提交 | 含义 |
|------|------|
| C | 创建登录页面结构 |
| D | 添加表单校验 |
| E | 修复样式问题 |

### 3.2 Squash Merge 后

执行压缩合并后，`main` 不会把 C、D、E 原封不动接过来，而是创建一个新的提交 S：

```bash
main:     A --- B --- S
                \
feature:         C --- D --- E
```

S 里面包含 C、D、E 的全部代码变化，但在 `main` 上只表现为一个提交。

你可以这样理解：

> C、D、E 是做菜过程中的切菜、炒菜、调味；S 是最终端上桌的成品菜。

---

## 四、Squash Merge 和普通 Merge 最大的区别

普通 Merge 会保留分支之间的连线，并生成一个 merge commit：

```bash
main:     A --- B -------- M
                \        /
feature:         C --- D
```

Squash Merge 不保留这种"从哪里分叉、又在哪里合回来"的合并关系：

```bash
main:     A --- B --- S

feature:         C --- D
```

所以它的特点是：

| 对比项 | 普通 Merge | Squash Merge |
|--------|------------|--------------|
| 是否保留分支连线 | 保留 | 不保留 |
| 是否生成 merge commit | 通常会 | 不会生成真正的 merge commit |
| 主分支是否干净 | 可能较复杂 | 很干净 |
| 功能分支的小提交是否进入主分支 | 会 | 不会，压成一个 |
| 适合场景 | 需要完整协作历史 | PR 合并、清理历史 |

---

## 五、命令怎么写？

最常见的命令如下：

```bash
git checkout main
git merge --squash feature
git commit -m "完成某某功能"
```

拆开理解：

1. `git checkout main`：先切换到主分支，因为你要把功能合到主分支。
2. `git merge --squash feature`：把 feature 的代码变化拿过来，但先不自动创建正式提交。
3. `git commit -m "完成某某功能"`：你手动创建一个新的提交，把这些变化一次性保存。

这里有一个关键点：

> `git merge --squash` 只是把变化放到暂存区附近，最终的提交需要你自己 `git commit`。

---

## 六、GitHub 上的 Squash and Merge

在 GitHub 或 GitLab 上合并 Pull Request 时，经常会看到三个按钮：

| 按钮 | 含义 |
|------|------|
| Create a merge commit | 普通合并，保留分支历史 |
| Squash and merge | 压缩合并，把 PR 压成一个提交 |
| Rebase and merge | 变基合并，保持线性历史 |

很多团队会要求：

> 一个 PR 对应一个 Squash Merge 提交。

这样做的好处是，主分支历史会像一份清晰的需求清单：

```bash
修复支付回调异常
新增订单导出功能
优化首页加载速度
升级用户权限模型
```

每一条都代表一个完整变更，而不是一堆过程性小修小补。

---

## 七、什么时候适合用 Squash Merge？

### 适合使用

| 场景 | 原因 |
|------|------|
| Pull Request 合并 | 让主分支只保留一个完整功能提交 |
| 功能分支有很多临时提交 | 清理 `fix typo`、`wip`、`try again` 这类噪音 |
| 一个 issue 对应一个功能 | 主分支历史更像任务完成记录 |
| 团队想保持主分支简洁 | 减少分支图复杂度 |

### 不太适合使用

| 场景 | 原因 |
|------|------|
| 需要保留每个提交的详细演进过程 | Squash 后过程会被压掉 |
| 每个提交都有独立审计价值 | 压缩后追溯粒度变粗 |
| 长期维护分支之间需要明确合并关系 | Squash 不保留合并连线 |

---

## 八、小白最容易混淆的地方

### Q1：Squash Merge 会不会丢代码？

不会。

它压缩的是**提交记录数量**，不是代码内容。C、D、E 的代码变化都会进入最终的 S 提交。

### Q2：Squash Merge 后 feature 分支还在吗？

通常还在，除非你手动删除它。

合并完成后，很多团队会删除已经完成的功能分支，因为它的价值已经进入主分支。

### Q3：Squash Merge 算不算真正的 merge？

从代码结果看，它确实把 feature 的改动合到了 main。

但从 Git 历史结构看，它不是传统意义上的 merge commit，因为它不记录两个父节点，也不保留分支合并关系。

---

## 九、一句话记忆

> **Squash Merge = 代码全拿走，历史压一个。**

它适合让主分支更干净，但不适合保留完整开发过程。


# 06 分支基本操作详细讲义：创建、切换、推送、删除
![[已生成图像 6.png]]

## 一、先把分支想象成"游戏存档路线"

学习分支操作前，先记住一个核心比喻：

> 分支就像游戏里的不同存档路线。

你可以有：

- `main`：正式路线，稳定可靠
- `feature/login`：登录功能路线
- `bugfix/payment`：修复支付问题路线
- `experiment/ui`：尝试新版界面路线

每条路线都可以独立前进，互不影响。等某条路线开发完成后，再把它合回主路线。

---

## 二、创建分支：开一条新路线

### 2.1 命令方式

只创建分支，但不切换过去：

```bash
git branch feature/login
```

创建并立刻切换过去：

```bash
git checkout -b feature/login
```

新版 Git 也可以写成：

```bash
git switch -c feature/login
```

### 2.2 图形工具里的操作

在 Git Graph 里，通常是在某个 commit 节点上右键，然后选择：

```text
Create Branch
```

这表示：

> 从这个 commit 开始，创建一条新分支。

### 2.3 小白要注意

你在哪个 commit 上创建分支，新分支就从哪里开始。

如果你在很旧的 commit 上创建分支，新分支就会从旧版本开始开发；如果你在 `main` 最新提交上创建分支，新分支就会基于最新代码。

---

## 三、切换分支：换到另一条路线

### 3.1 命令方式

```bash
git checkout feature/login
```

或：

```bash
git switch feature/login
```

### 3.2 Git Graph 里的关键动作

一定要右键**分支标签的矩形区域**，选择：

```text
Checkout Branch
```

不要随便在 commit 标题上 checkout。

因为：

- checkout 分支标签：HEAD 指向分支，是正常状态
- checkout 某个 commit：HEAD 直接指向提交，可能进入 detached HEAD

### 3.3 用一句话判断是否安全

> 你要切换的是"分支名"，不是"某个历史节点"。

如果你只是想回看旧代码，可以 checkout 某个 commit；但如果你要继续开发，应该先创建分支，再在分支上工作。

---

## 四、推送分支：把本地路线同步到远程

### 4.1 为什么要 push？

本地分支只存在你电脑上。别人看不到，也不能协作。

执行 push 后，远程仓库才会出现对应的远程分支，比如：

```bash
本地：feature/login
远程：origin/feature/login
```

### 4.2 第一次推送新分支

```bash
git push -u origin feature/login
```

这里的 `-u` 表示建立跟踪关系。

以后你在这个分支上就可以直接：

```bash
git push
```

Git 会知道你要推到远程的哪个分支。

### 4.3 三种推送方式

| 方式 | 命令 | 适合场景 |
|------|------|----------|
| 普通推送 | `git push` | 没改写历史，最常用 |
| 强制推送 | `git push --force` | 覆盖远程，风险较高 |
| 安全强推 | `git push --force-with-lease` | rebase 后推荐使用 |

小白记住：

> 普通开发先用 `git push`；rebase 后需要强推时，优先用 `--force-with-lease`。

---

## 五、删除分支：删除路线标签

### 5.1 删除本地分支

删除已经合并的分支：

```bash
git branch -d feature/login
```

强制删除未合并分支：

```bash
git branch -D feature/login
```

`-D` 更危险，因为它会删除还没有合并的分支标签。

### 5.2 删除远程分支

```bash
git push origin --delete feature/login
```

这表示告诉远程仓库：

> 请把 `origin/feature/login` 这个远程分支删除。

### 5.3 删除分支到底删除了什么？

删除分支通常删除的是**分支指针**，不是立刻删除 commit 本身。

但是如果某些 commit 没有任何分支、标签或 HEAD 能找到它们，它们会变成"无人引用的提交"。短期内可以用 `git reflog` 找回，时间久了可能被 Git 垃圾回收清理。

---

## 六、重命名分支

### 6.1 重命名当前本地分支

```bash
git branch -m new-name
```

### 6.2 重命名其他本地分支

```bash
git branch -m old-name new-name
```

### 6.3 远程分支为什么不能直接改名？

远程分支没有真正的"重命名"按钮，本质操作是三步：

1. 本地分支改名
2. 推送新名字到远程
3. 删除远程旧名字

命令示例：

```bash
git branch -m old-name new-name
git push -u origin new-name
git push origin --delete old-name
```

---

## 七、查找分支和提交

### 7.1 Git Graph 里搜索

在 Git Graph 页面按：

```text
Ctrl + F
```

可以搜索：

- 分支名称
- commit 标题
- 部分关键字

### 7.2 命令行查看分支图

```bash
git log --oneline --graph --decorate --all
```

拆开看：

| 参数 | 含义 |
|------|------|
| `--oneline` | 每个提交只显示一行 |
| `--graph` | 显示分支图形 |
| `--decorate` | 显示分支名、标签名 |
| `--all` | 显示所有分支 |

---

## 八、小白操作口诀

| 任务 | 口诀 |
|------|------|
| 开始新功能 | 先从最新 `main` 创建新分支 |
| 切换分支 | 点分支标签，不点 commit 标题 |
| 推送分支 | 新分支第一次用 `git push -u` |
| 删除分支 | 已合并用 `-d`，未合并慎用 `-D` |
| 改远程分支名 | 新推一个，再删旧的 |

> **分支操作的核心：创建是贴标签，切换是移动 HEAD，推送是同步远程，删除是移除标签。**


# 07 合并冲突与 Fast-Forward 详细讲义：为什么有时合并很顺，有时会冲突
![[已生成图像 7.png]]

## 一、先理解：为什么会有冲突？

Git 合并时，本质是在问一个问题：

> 两条分支修改的内容，能不能自动拼在一起？

如果两个人改的是不同文件，通常没问题。

如果两个人改的是同一个文件的不同位置，Git 也常常能自动处理。

但如果两个人改的是同一个文件的同一块内容，Git 就不知道该听谁的，于是产生冲突。

---

## 二、什么是合并冲突？

假设 `main` 分支和你的 `feature` 分支都改了同一行文案：

`main` 改成：

```text
按钮文案：立即购买
```

`feature` 改成：

```text
按钮文案：马上下单
```

Git 没有业务判断能力，它不知道哪一句才是正确需求，所以会把问题交给你：

```text
<<<<<<< HEAD
按钮文案：马上下单
=======
按钮文案：立即购买
>>>>>>> main
```

这就是冲突标记。

---

## 三、冲突标记怎么看？

| 标记 | 含义 |
|------|------|
| `<<<<<<< HEAD` | 当前分支的内容，也就是你现在所在分支的内容 |
| `=======` | 分隔线，上下两边是两种版本 |
| `>>>>>>> main` | 传入分支的内容，也就是被合并进来的分支内容 |

在 VS Code 或 Git Graph 的可视化界面里，经常会显示成：

| 颜色/区域 | 含义 |
|-----------|------|
| 当前更改 | 你当前分支上的内容 |
| 传入更改 | 对方分支或目标分支传进来的内容 |
| 同时保留 | 两边都保留 |

---

## 四、解决冲突的标准步骤

### 4.1 命令行流程

```bash
git merge main
```

如果出现冲突：

1. 打开冲突文件
2. 删除冲突标记
3. 保留正确内容
4. 添加到暂存区
5. 继续完成合并

命令如下：

```bash
git add <resolved-file>
git commit
```

如果是在 rebase 过程中解决冲突，最后一步不是 `git commit`，而是：

```bash
git rebase --continue
```

### 4.2 可视化工具流程

在 VS Code 里通常是：

1. 打开左侧有冲突标识的文件
2. 查看当前更改和传入更改
3. 选择保留哪一边，或手动编辑成第三种正确结果
4. 点击文件旁边的加号，把文件标记为已解决
5. 点击继续合并或继续 rebase

---

## 五、解决冲突不是选边站

很多小白以为冲突只有两种答案：

- 保留我的
- 保留对方的

其实还有第三种，也是工作中最常见的一种：

> 你手动把两边的正确部分组合成一个新版本。

例如：

```text
当前分支：按钮文案：马上下单
传入分支：按钮文案：立即购买
最终结果：按钮文案：立即购买并下单
```

Git 只负责提醒你"这里我不会判断"，最终业务逻辑要靠人来决定。

---

## 六、什么是 Fast-Forward？

Fast-Forward 可以翻译成"快进合并"。

它发生在一种很简单的情况下：

> 当前分支没有新的独立提交，只是落后于另一个分支。

例如：

```bash
main:     A --- B
feature:         C --- D
```

这里可以理解为：`feature` 只是从 `main` 后面继续走了几步，而 `main` 自己没有走别的岔路。

合并时，Git 不需要创建新的合并提交，只需要把 `main` 指针向前移动到 D：

```bash
main:     A --- B --- C --- D
```

这就叫 Fast-Forward。

---

## 七、Fast-Forward 和 Merge Commit 的区别

| 对比项 | Fast-Forward | 普通 Merge Commit |
|--------|--------------|-------------------|
| 是否创建新提交 | 不创建 | 创建一个 merge commit |
| 分支图形 | 一条直线 | 有分叉和汇合 |
| 适用情况 | 当前分支没有新提交 | 两边都各自发展过 |
| 历史可读性 | 简洁 | 合并关系更明确 |

### 如何强制不要 Fast-Forward？

```bash
git merge --no-ff feature
```

这表示：

> 即使 Git 可以直接快进，也请生成一个合并提交。

这样做的好处是，未来看历史时能清楚知道："这里曾经合入过一个功能分支。"

---

## 八、什么时候选择哪种？

| 情况 | 建议 |
|------|------|
| 个人小功能，提交很少 | Fast-Forward 很清爽 |
| 团队功能分支，需要保留上下文 | `merge --no-ff` 更清楚 |
| 主分支要求严格审计 | 保留 merge commit |
| 只是同步远程最新提交 | Fast-Forward 就够 |

---

## 九、冲突处理口诀

> **先看文件，再看两边；不是选赢输，而是合成正确答案。解决后 add，merge 就 commit，rebase 就 continue。**


# 08 Stash 与 Cherry-Pick 详细讲义：临时收纳和单点摘取
![[已生成图像 8.png]]

## 一、Stash 是什么？

`stash` 的意思是"临时藏起来"。

在 Git 里，它的作用是：

> 把你还没提交的改动临时收起来，让工作区恢复干净。

这非常适合下面这种情况：

1. 你正在 `feature/login` 分支上写代码
2. 代码还没写完，不适合 commit
3. 突然有人让你切到 `main` 修一个紧急 bug
4. 但 Git 不让你切分支，因为当前改动可能被覆盖

这时就可以用 stash。

---

## 二、Stash 的生活比喻

你正在桌上写作业，桌面很乱。突然老师让你马上换一套试卷。

你不想把当前作业交上去，也不想丢掉它，于是你把桌上的东西先装进一个文件袋。

这个文件袋就是 stash。

- 桌面 = 工作区
- 文件袋 = stash
- 把东西装进去 = `git stash`
- 再拿出来 = `git stash pop` 或 `git stash apply`

---

## 三、Stash 常用命令

| 命令 | 含义 |
|------|------|
| `git stash` | 暂存当前未提交改动 |
| `git stash save "说明"` | 带说明地暂存改动 |
| `git stash list` | 查看所有 stash |
| `git stash pop` | 应用最近的 stash，并删除它 |
| `git stash apply` | 应用最近的 stash，但保留记录 |
| `git stash drop` | 删除某条 stash |

现在更推荐的带说明写法是：

```bash
git stash push -m "登录页写到一半"
```

---

## 四、Pop 和 Apply 的区别

这是小白最容易混的地方。

| 操作 | 应用改动 | stash 记录还在吗 | 适合场景 |
|------|----------|------------------|----------|
| `git stash pop` | 会 | 不在了 | 确认只需要恢复一次 |
| `git stash apply` | 会 | 还在 | 想多次尝试，或怕恢复失败 |
| `git stash drop` | 不应用 | 删除 | 确认不要这份临时改动 |

简单记忆：

> pop = 拿出来并清空盒子；apply = 拿出来但盒子还留着。

---

## 五、Cherry-Pick 是什么？

`cherry-pick` 字面意思是"摘樱桃"。

在 Git 里，它的作用是：

> 从别的分支上挑一个指定 commit，复制到当前分支。

注意，它不是把整个分支合过来，而是只拿某一个提交。

---

## 六、Cherry-Pick 的图形理解

假设功能分支上有三个提交：

```bash
feature: A --- B --- C
```

其中：

| 提交 | 内容 |
|------|------|
| A | 新增页面结构 |
| B | 修复一个安全漏洞 |
| C | 调整页面样式 |

现在 `main` 只需要 B 这个安全修复，不需要 A 和 C。

你可以切到 `main`，然后执行：

```bash
git cherry-pick <B的哈希值>
```

结果是：

```bash
main: X --- Y --- B'
```

为什么是 B'？

因为 cherry-pick 也是把 B 的变化复制一份放到当前分支上，新提交会有新的哈希。

---

## 七、Cherry-Pick 的典型场景

### 场景一：只想拿一个 bug 修复

某个开发者在自己的分支上修好了高危漏洞，但整个功能分支还不能合并。

这时其他分支可以 cherry-pick 这个修复提交，把安全修复先拿过来。

### 场景二：功能分支里混进了别的需求

你在开发 A 功能时，顺手提交了一个 B 功能的小修复。

如果 B 功能应该先上线，就可以把那个提交 cherry-pick 到主分支或发布分支。

### 场景三：拆分历史

一条长分支里有一个提交不想要，可以新建分支，然后把需要的提交一个个 cherry-pick 过去。

提交少时可以这样做；提交多时通常用交互式 rebase 更方便。

---

## 八、Stash 和 Cherry-Pick 的区别

| 对比项 | Stash | Cherry-Pick |
|--------|-------|-------------|
| 处理对象 | 未提交的改动 | 已经提交的 commit |
| 目的 | 临时收起来 | 单独拿某个提交 |
| 是否产生新提交 | 不一定 | 会产生新提交 |
| 常见场景 | 切分支前保存现场 | 把某个修复复制到另一个分支 |

---

## 九、小白安全建议

1. stash 前最好写说明，避免过几天忘了里面是什么。
2. cherry-pick 前先确认自己在哪个分支上，因为提交会落到当前分支。
3. cherry-pick 后如果有冲突，处理方式和 merge 冲突类似：解决文件、`git add`、继续。
4. 不要把 cherry-pick 当成长期协作的主要方式，它适合点状搬运，不适合大规模同步。

---

## 十、一句话记忆

> **Stash 是把没提交的东西临时收起来；Cherry-Pick 是把已经提交的某一个点单独搬过来。**


# 09 交互式 Rebase 与 Soft Reset 详细讲义：整理提交历史
![[已生成图像 9.png]]

## 一、为什么要整理提交历史？

写代码时，我们的提交历史经常是这样的：

```bash
实现登录
修一下登录
再修一下
改错别字
终于好了
补测试
```

开发过程中这样没问题，因为小步提交能保护进度。

但在合并到主分支前，团队通常希望提交历史变得更清晰：

```bash
实现登录功能
补充登录功能测试
```

整理提交历史的常用工具有两个：

- 交互式 Rebase：可以改、压、删、重排最近的一段提交
- Soft Reset：可以把最近几个提交退回暂存区，再重新提交

---

## 二、交互式 Rebase 是什么？

普通 rebase 是自动把提交搬到新位置。

交互式 rebase 则是在搬运前给你一个编辑清单，让你决定每个提交怎么处理。

命令格式：

```bash
git rebase -i HEAD~n
```

这里的 `n` 表示最近几个提交。

例如：

```bash
git rebase -i HEAD~4
```

意思是：我要整理最近 4 个提交。

---

## 三、交互式 Rebase 的操作菜单

打开后你会看到类似这样的内容：

```bash
pick a1b2c3d 实现登录页面
pick b2c3d4e 修复按钮样式
pick c3d4e5f 改错别字
pick d4e5f6g 补充登录测试
```

每一行前面的 `pick` 可以改成其他操作。

| 操作 | 含义 | 小白理解 |
|------|------|----------|
| `pick` | 保留提交 | 这条保留不动 |
| `reword` | 修改提交信息 | 内容不变，只改标题 |
| `squash` | 压缩到上一个提交 | 和上一条合并，并保留提交说明 |
| `fixup` | 压缩到上一个提交 | 和上一条合并，但丢掉自己的提交说明 |
| `drop` | 删除提交 | 这条不要了 |

---

## 四、用交互式 Rebase 删除中间提交

假设你有 4 个提交：

```bash
A --- B --- C --- D
```

其中 C 是不小心提交的测试文件，你想删掉它。

执行：

```bash
git rebase -i HEAD~4
```

把 C 那一行从：

```bash
pick c3d4e5f 提交测试文件
```

改成：

```bash
drop c3d4e5f 提交测试文件
```

保存退出后，Git 会重新生成历史：

```bash
A --- B --- D'
```

注意 D 变成 D'，因为它的位置和父节点变了，所以哈希也会变。

---

## 五、用交互式 Rebase 压缩提交

假设有三条提交：

```bash
pick a1b2c3d 实现登录页面
pick b2c3d4e 修复登录按钮样式
pick c3d4e5f 改登录文案错别字
```

如果后两条只是对第一条的修修补补，可以改成：

```bash
pick a1b2c3d 实现登录页面
squash b2c3d4e 修复登录按钮样式
fixup c3d4e5f 改登录文案错别字
```

结果是三条提交变成一条更完整的提交：

```bash
实现登录页面
```

---

## 六、Soft Reset 是什么？

`git reset --soft` 可以把最近几个提交"撤回"，但保留改动，并且保留在暂存区。

命令：

```bash
git reset --soft HEAD~n
```

例如：

```bash
git reset --soft HEAD~3
```

意思是：

> 把最近 3 个提交取消掉，但这些提交里的文件改动不要丢，全部放回暂存区。

然后你可以重新提交：

```bash
git commit -m "完成登录功能"
```

---

## 七、Soft、Mixed、Hard 的区别

| 命令 | 提交会退回吗 | 改动保留在哪里 | 是否危险 |
|------|--------------|----------------|----------|
| `git reset --soft` | 会 | 暂存区 | 相对安全 |
| `git reset --mixed` | 会 | 工作区 | 中等，需要重新 add |
| `git reset --hard` | 会 | 不保留，直接丢弃 | 高风险 |

小白记住：

> 不确定时不要用 `--hard`。它不仅退提交，还会丢工作区改动。

---

## 八、交互式 Rebase 和 Soft Reset 怎么选？

| 需求 | 推荐 |
|------|------|
| 只想把最近几个提交压成一个 | `git reset --soft HEAD~n` |
| 想删除中间某个提交 | 交互式 rebase |
| 想修改某个提交信息 | 交互式 rebase |
| 想调整提交顺序 | 交互式 rebase |
| 想精细整理多条提交 | 交互式 rebase |

Soft Reset 像一键撤回最近几步，然后重新打包。

交互式 Rebase 像打开提交清单，逐条编辑。

---

## 九、整理历史后的推送问题

只要你修改了已经推送到远程的提交历史，就可能遇到普通 push 被拒绝。

因为远程还保存着旧历史，而你本地已经变成新历史。

这时应该使用：

```bash
git push --force-with-lease
```

不要优先使用：

```bash
git push --force
```

原因前面讲过：`--force-with-lease` 会先检查远程有没有别人新提交，能减少误覆盖风险。

---

## 十、小白安全流程

1. 整理历史前，先确认当前分支是不是自己的个人功能分支。
2. 不要在多人共用分支上随便 rebase 或 reset。
3. 操作前先 `git status`，确保自己知道工作区是否干净。
4. 如果已经推送过，整理后用 `--force-with-lease`。
5. 如果操作错了，先不要慌，优先看 `git reflog` 找回旧位置。

---

## 十一、一句话记忆

> **交互式 Rebase 是精修历史，Soft Reset 是把最近几个提交退回去重新打包。**


# 10 Rebase vs Merge 选择讲义：什么时候该选哪一个
![[已生成图像 10.png]]

## 一、为什么需要选择策略？

Git 不是只有一种合并方式。

同样是把一个分支的代码放到另一个分支里，你可以选择：

- Merge
- Rebase
- Squash Merge

这三种方式代码结果可能很接近，但历史形状完全不同。

选择策略，本质是在回答一个问题：

> 我更想保留完整过程，还是更想让历史简洁好读？

---

## 二、三种策略先总览

| 策略 | 一句话理解 | 历史形状 |
|------|------------|----------|
| Merge | 两条线汇合，保留关系 | 分叉后合并 |
| Rebase | 把自己的提交复制到别人后面 | 一条直线 |
| Squash Merge | 把一串提交压成一个 | 主分支很简洁 |

---

## 三、什么时候用 Merge？

### 适合场景

Merge 适合你想保留完整开发脉络的时候。

例如：

- 一个长期功能分支开发了很多天
- 多个人在同一个功能分支上协作
- 你想清楚看到分支从哪里分出来、在哪里合回去
- 项目需要完整审计历史

### 为什么 Merge 安全？

因为 Merge 不改写原来的提交历史。

原来的 commit 哈希不会变，别人基于这些提交做的工作也不会突然失效。

### Merge 的代价

历史会更复杂。

当很多人频繁 merge 时，Git Graph 里会出现大量分叉和汇合，看起来像一张很复杂的交通图。

---

## 四、什么时候用 Rebase？

### 适合场景

Rebase 适合个人功能分支跟进主分支。

例如：

```bash
git checkout feature/login
git rebase main
```

这表示：

> 把我的登录功能提交，搬到最新 main 后面。

这样后续合并时，历史会很线性。

### Rebase 的好处

- 不产生 merge commit
- 历史是一条直线
- 看日志更容易
- 减少 Git Graph 的横向宽度

### Rebase 的风险

Rebase 会改写历史。

如果别人已经基于你的分支继续开发，你 rebase 后就会让别人的基础提交变成旧版本，协作会变得混乱。

所以小白记住：

> 自己的分支可以 rebase，公共分支谨慎 rebase，多人共用分支不要随便 rebase。

---

## 五、什么时候用 Squash Merge？

### 适合场景

Squash Merge 适合合并 Pull Request。

例如，一个 PR 里有很多临时提交：

```bash
写页面
修样式
补接口
改命名
修测试
```

合入主分支后只保留：

```bash
新增订单详情页面
```

这能让主分支历史非常清楚。

### Squash 的取舍

好处：

- 主分支很干净
- 一个 PR 对应一个提交
- 查历史时很像看功能清单

代价：

- 不保留原始小提交
- 不保留真实分支合并关系
- 想追溯细节时，需要回到 PR 页面看讨论和提交

---

## 六、选择策略速查表

| 情况 | 推荐策略 | 原因 |
|------|----------|------|
| 个人功能分支同步最新主分支 | Rebase | 保持线性历史 |
| 功能完成后合入主分支 | Merge 或 Squash | 看团队是否要保留完整过程 |
| GitHub PR 合并 | Squash Merge | 主分支干净，一个 PR 一个提交 |
| 多人共用一个分支开发 | Merge | 不改写别人依赖的历史 |
| 分支已经有 merge 历史 | Merge | 再 rebase 容易制造重复历史 |
| 需要审计完整过程 | Merge --no-ff | 保留清楚的合并节点 |
| 只想清理最近几个零碎提交 | Interactive Rebase 或 Soft Reset | 整理提交历史 |

---

## 七、一个实际工作流示例

假设你要开发登录功能。

### 第一步：从最新 main 创建功能分支

```bash
git checkout main
git pull
git checkout -b feature/login
```

### 第二步：在自己的分支上小步提交

```bash
git add .
git commit -m "创建登录页面"
git add .
git commit -m "添加登录校验"
git add .
git commit -m "补充错误提示"
```

### 第三步：开发期间跟进 main

如果 main 有新提交，你可以在自己的分支上：

```bash
git rebase main
```

如果团队不允许 rebase，也可以：

```bash
git merge main
```

### 第四步：提交 PR

推送分支：

```bash
git push -u origin feature/login
```

然后在 GitHub 或 GitLab 上创建 Pull Request。

### 第五步：合并 PR

常见团队会选择：

```text
Squash and merge
```

这样主分支只留下：

```bash
新增登录功能
```

---

## 八、最重要的协作原则

### 原则一：公共历史不要随便改

凡是别人可能已经拉取、基于它继续开发的分支，都不要随便 rebase 或 reset。

### 原则二：强推前先想清楚

看到 `--force` 或 `--force-with-lease`，就要意识到：

> 我正在覆盖远程历史。

优先用 `--force-with-lease`，并确认没有覆盖他人工作。

### 原则三：团队规范高于个人偏好

有些团队喜欢 Merge，因为审计完整。

有些团队喜欢 Squash，因为主分支清爽。

有些团队要求所有 PR 先 Rebase 再合并。

没有绝对唯一正确，关键是整个团队统一。

---

## 九、最终口诀

| 口诀 | 含义 |
|------|------|
| 想保留过程，用 Merge | 分支历史完整可追溯 |
| 想保持直线，用 Rebase | 适合个人分支整理 |
| 想主线干净，用 Squash | 适合 PR 合并 |
| 涉及别人，别乱改历史 | 避免协作事故 |
| 强推优先 lease | 减少覆盖他人提交 |

> **Merge 记录真实发生过什么，Rebase 整理成更好读的样子，Squash 把一个需求收束成一个结果。**
