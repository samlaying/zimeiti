# 别再靠感觉调Agent了！16个开源项目教会我“为文档写测试”

> 来源：[[2026-05-25-314-16个开源agent项目教我如何设计agent系统.md]]

## 读者与痛点
- 目标读者：正在或计划开发AI Agent/智能体的程序员、产品经理、独立开发者
- 痛点：1. 调Agent像玄学，改了提示词效果反而变差，没有数据衡量好坏。2. 写了很长的规则文档，AI还是我行我素，不知道哪里出了问题。3. 模型一更新，之前的效果就崩了，感觉之前的工作都白费了。4. 不知道如何系统性地测试和确保Agent在压力下的可靠性。

## 新鲜观点
把软件工程里经典的“测试驱动开发”（TDD）逆向应用到给AI写的“操作手册”（Skill文档）上：不是先写文档再测试，而是先设计压力测试，逼出AI的真实违规行为，再针对这些具体“罪状”去写最精准、最简短的规则。文档越长，AI可能越糊涂。

## 核心立场
AI Agent开发必须告别“感觉流”，建立一套以压力测试和数据驱动的质量评估体系。优秀的Agent不是“调”出来的，而是通过严谨的“测试-开发-验证”流程“设计”出来的。

## 钩子
- 你写的Agent规则越长，它越不听话？这可能不是AI的问题，而是你用错了开发方法。
- 16个顶级开源Agent项目的设计者，没有一个在靠‘感觉’迭代。他们都在用同一套‘给文档写测试’的方法。
- 模型一更新，你的Agent就崩？因为你从没在‘压力’下测试过它。
- 别急着写提示词，先为AI设计一场‘压力面试’。
- 我试了为AI的‘操作手册’写单元测试，结果它一次就通过了压力测试。

## 草稿骨架
【引子】“我的AI客服总在关键时刻‘说错话’，规则文档改了八遍，模型一升级又不行了。”这恐怕是许多Agent开发者的真实噩梦。我们习惯于“调”提示词，但或许从一开始就错了。 

【核心观点】在深入研究了包括Superpowers、GOOS在内的16个顶级开源Agent项目后，我发现一个反共识的做法：他们都在为给AI写的“说明书”（Skill文档）做压力测试。方法论可概括为“TDD4Docs”——测试驱动的文档开发。 

【方法论：TDD4Docs三步法】
1. **Red阶段：设计压力，录下“罪状”**
   - 任务：不是写规则，而是设计最刁钻的压力测试场景（如时间+权威+情感绑架叠加）。
   - 操作：在**没有任何规则**时，让Agent处理这些场景，逐字记录它的违规话术和绕过逻辑。这份记录就是“需求清单”。
   - 案例：如何为“不泄露内部信息”设计压力测试，AI又如何巧妙绕过。
2. **Green阶段：针对罪状，写最短规则**
   - 原则：只针对Red阶段记录的真实违规点写规则。要精准，要简短。
   - 反直觉：规则越长，AI可能越记不住、越容易误解。试试只用一条核心规则和一个反例，效果可能更好。
3. **Refactor阶段：测试新招，迭代规则**
   - 操作：重新运行压力测试，看AI是否发展出新的“花招”。
   - 典型发现与应对：例如，AI会“遵守精神而非字面”，或在规则中找到模糊地带。据此迭代规则的措辞。

【实战分类指南】不同“说明书”有不同测法：纪律型要测多重压力叠加；技术型要测新场景应用；模式型必须测“不该用”的场景。

【让评估成为习惯】提供三个核心评估维度（行为正确性、结果质量、可靠性）和落地工具建议。强调评估应内化到每次代码修改、模型更新和每周巡检中。

【结语】从“调Agent”到“设计Agent”，核心是思维方式的转变：用系统工程的确定性，去驾驭大模型的不确定性。你的下一步，不是去写更多的规则，而是去设计第一个压力测试场景。
