# 图工程来了：AI产品经理，别再只会调 Prompt 了

> 一篇基于《过程.md》整理的公众号文章草稿。

## 标题备选

1. 图工程来了：AI产品经理，别再只会调 Prompt 了
2. 为什么你的 Agent 总是不稳定？问题可能不在模型，而在产品设计
3. 做 AI 产品，最重要的能力不是写 Prompt，而是设计系统怎么运转

## 正文

你有没有遇到过这样的情况？

你和研发说：“做一个智能客服，用户问什么，它都能回答。”

产品上线后，好的时候像个专家，差的时候像个刚入行的实习生。用户说 AI 答错了，你想优化，却不知道该改哪里：是提示词有问题，还是工具没调对，还是整个流程就没设计清楚？

更麻烦的是，过了一段时间，负责这个 Agent 的同事离职了。留给你的不是一套清晰的产品架构，而是一堆 Prompt、工具和补丁。你只能继续打补丁，直到系统变成谁也不敢动的黑盒。

这可能不是模型能力不够，而是你从一开始就把所有事情交给了一个 Agent。

最近 LangChain 团队在总结三年 LangGraph 实践时，提到了一个正在流行的新词：Graph Engineering，图工程。

### 背景：为什么又出现了一个“工程”新词？

图工程是最近从 X 的 AI 内容生态里冒出来的新术语。它和 Prompt Engineering（提示工程）、Context Engineering（上下文工程）、Harness Engineering（框架工程）、Loop Engineering（循环工程）一样，都是这一轮 AI 实践中不断出现的新概念。

把它们称为“流行词”并不算错。毕竟，AI 圈每隔一段时间就会出现一批新词。但这些词之所以不断出现，也有现实原因：它们确实对应着构建者正在面对的真实问题和工程决策。

归根结底，我们想做的事情很简单：利用大语言模型的能力，替我们完成一些有用的工作。

无论你使用 Prompt、Agent、Loop 还是 Graph，它们都只是实现方式。之所以会出现这么多不同的术语，是因为让大语言模型真正稳定地干活，并没有想象中容易。

大语言模型是一种新的软件形态。它不像传统程序那样完全稳健、确定、可预测。我们一直在尝试新的方法，让它能够更可靠地完成任务，而这些新方法就逐渐形成了新的工程概念。

所以，先把“流行词”放到一边。把 Agent 系统表示成图，也就是所谓的“图工程”，本质上是一种非常合理的方式：它让构建者可以把自己对系统运行方式的理解，放进一条更受约束的路径里，而不是把所有判断都交给大语言模型。

更具体地说，当你希望 Agent 按照某些明确路径工作时，图工程可以帮助你更紧密地控制它的行为。

这正是 LangChain 团队三年前构建 LangGraph 的出发点：用一个框架，帮助开发者构建这类 Agent 系统。原文提到，如今 LangGraph 每月下载量已经超过 6500 万次，使用者包括初创公司和大型企业。

在众多 Agent 框架中，LangGraph 能够流行起来，一个重要原因是它在两件事之间取得了平衡：一边是确定性的流程路径，另一边是 Agent 的自主判断。

接下来要讲的，就是这种“确定性”和“灵活性”如何被放进同一个 Agent 系统里。

它听起来像一个技术名词，但对 AI 产品经理来说，更像是一种工作方式：

> 在让 AI 开始干活之前，先把这件事应该怎么运转想清楚。

### 一、你踩过的坑，可能都是“没设计流程”

很多 AI 产品的需求文档，写起来非常简单：

用户输入问题，系统理解需求，调用相关工具，最后给出答案。

但真正开始做之后，问题会一个接一个地出现。

用户的问题要不要先分类？

数据查不到怎么办？

工具调用失败要不要重试？

哪些事情可以让 AI 自己决定？

哪些操作必须经过用户确认？

如果答案不可靠，系统应该怎么兜底？

如果这些问题没有在设计阶段被回答，系统就只能把判断全部交给模型。

模型当然可以帮你做很多事，但它并不总是稳定、确定、可预测的软件。它可能这次理解正确，下次换一种表达就走向了另一条路径。出了问题，你也很难判断到底是哪个环节出了错。

这就是第一个坑：把所有事都交给一个 Agent。

第二个坑，是出了问题却不知道怎么改。

用户说“AI 回答错了”，你只能把对话复制给研发，再说一句：“帮忙优化一下。”研发可能改了 Prompt，结果这个问题好了，另一个问题又出现了。

因为系统没有被拆开，你没有办法准确回答：

- 是客户资料没查到？
- 是客户阶段判断错了？
- 是 AI 生成建议时出现了幻觉？
- 还是发送动作本身没有经过确认？

第三个坑，是接手一个 Agent 产品之后无从下手。

当整个系统只有“输入—模型—输出”这条模糊链路时，产品经理的工作就会慢慢变成调 Prompt。每次出问题，加一条规则；每次有新需求，再补一个例外。时间久了，没人知道系统为什么这样工作，也没人敢删掉旧逻辑。

问题的本质是：你没有定义系统应该如何运转。

### 二、图工程到底是什么？

一句话说，图工程就是：

> 先画好一张流程图，规定每一步该做什么、由谁来做、出错了怎么办，再决定哪些环节交给 AI。

可以把它想象成管理一个团队。

有一种管理方式，是招一个“全能员工”，然后告诉他：“帮客户解决问题。”之后就放手不管。

这个员工能力很强，有时能独立处理复杂问题；但有时也会做出让人无法理解的决定。出了问题，你不知道他是在理解需求、查资料，还是执行动作时犯了错。

还有一种管理方式，是先把服务流程设计清楚：

第一步接待客户，第二步判断需求，第三步分配给不同的人处理，第四步确认结果，第五步完成交付。

简单、固定的步骤，让代码来执行；需要综合判断的步骤，交给 AI；可能带来风险的关键动作，必须经过校验或人工确认。

图工程就是第二种方式。

比如，你要做一个销售助手，帮助销售管理客户跟进。

你不会一上来就对 AI 说：“帮我管理客户。”

你会先把工作拆成几步：

1. 查询客户资料：这是固定动作，直接读取数据库，不需要 AI 判断。
2. 判断客户阶段：需要结合沟通记录和行为信息进行分析，可以交给 AI。
3. 生成跟进建议：需要理解上下文并组织语言，可以交给 AI。
4. 发送邮件、更新系统：这是确定性动作，而且有真实业务风险，最好由代码执行，并在关键节点要求确认。

这四步连起来，就是一个基本的 Agent 工作流。

它的重点不在于画图本身，而在于你开始明确：

- 哪些事情应该固定下来；
- 哪些事情需要模型判断；
- 每一步的输入和输出是什么；
- 如果失败，下一步应该怎么走；
- 哪些操作不能让 AI 自己做决定。

这比单纯写一段“聪明的 Prompt”更接近产品设计。

### 三、图工程会怎样改变 AI 产品经理的工作？

#### 1. 你终于能把需求写清楚了

以前的需求可能是：

> 用户输入问题，系统分析后给出建议。

研发接着会问：分析失败了怎么办？建议需要用户确认吗？数据查不到怎么办？

如果这些问题你答不上来，不是研发在故意为难你，而是需求本身还没有被设计完整。

用图工程思维，你会在需求阶段就把这些内容定义清楚：每一步由代码还是 AI 完成，输入是什么，输出是什么，错误怎么处理，哪些地方需要用户介入。

研发拿到的就不再是一句模糊的“做一个智能助手”，而是一套可以讨论、实现和验收的系统行为。

#### 2. 你终于能定位问题了

用户再说“AI 答错了”时，你不必只能把问题转给研发。

你可以沿着流程去看：

- 如果客户信息没有拉到，是资料查询节点的问题；
- 如果把初步接触的客户判断成了商机，是客户阶段分析节点的问题；
- 如果前面信息都正确，但建议不合适，是方案生成节点的问题；
- 如果建议没问题，却未经确认就发出去了，是执行和权限控制的问题。

当问题被定位到具体节点，优化就不再是“再调一调 Prompt”，而是可以讨论数据、规则、模型、流程和权限。

系统从一个黑盒，变成了一条可以逐段检查的路径。

#### 3. 你终于能设计评测方案了

以前验收 AI 产品，常见的说法是：“感觉有时候不太准。”

但“感觉”无法告诉团队应该改什么，也无法判断下一版到底有没有变好。

图工程思维会让你把评测拆开：

- 整个流程有没有完成，有没有漏掉关键步骤；
- 每个节点的判断是否准确；
- 数据查不到时，系统是否正确兜底；
- AI 有没有执行不该执行的动作；
- 高风险操作是否经过用户确认。

这样一来，产品验收就从“整体感觉不错”，变成了有流程完成率、节点准确率和边界安全性的具体标准。

这也是图工程真正有价值的地方：它让 AI 产品从“能不能回答”，走向“能不能稳定地完成一项工作”。

### 四、图工程不是把 AI 变成死流程

有人可能会担心：如果每一步都提前规定好，Agent 还算智能吗？

答案是，图工程并不是把所有决策都写死，而是把确定的部分固定下来，把需要判断的部分留给 AI。

真实的 Agent 工作流往往不是一条从头走到尾的直线。它可能需要重试失败的工具调用，等待用户补充信息，经过校验后重新生成答案，也可能在关键节点暂停，等待人工确认。

所以，好的系统不是“全自动”，也不是“全手工”，而是让代码处理确定性，让 AI 处理复杂判断，让流程负责边界和协作。

真正成熟的 Agent，应该同时具备两种能力：

一部分路径足够稳定，另一部分步骤保留足够灵活。

### 五、产品经理明天就能开始的做法

如果你正在设计一个 Agent 产品，可以先不要急着写 Prompt，拿一张纸回答五个问题：

1. 用户的目标到底是什么？不要只写“获得答案”，要写清楚最终要完成的业务动作。
2. 从输入到结果，中间必须经过哪些步骤？把流程拆出来。
3. 每一步由谁来做？代码、单次模型调用、完整 Agent，还是人工？
4. 每一步的输入、输出和失败处理是什么？
5. 哪些地方必须评测，哪些动作必须确认？

写完之后，再回头决定 Prompt 怎么写、工具怎么接、模型用哪个。

这时你会发现，Prompt 只是系统中的一个节点，而不是整个产品。

### 结尾

图工程不是一个新技术，也不只是又一个 AI 时代的流行词。

它提醒产品经理回到一个很朴素的道理：

> 在让 AI 做事情之前，你得先想清楚这件事本来应该怎么做。

这不就是产品经理最该干的事吗？
