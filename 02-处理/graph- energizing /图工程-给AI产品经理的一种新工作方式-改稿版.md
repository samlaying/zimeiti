# AI 产品经理工作流｜Agent 越调越乱，问题不在 Prompt

> 基于《过程.md》和《改稿方法论.md》重写的公众号稿件。



**AI 产品经理如何用 Graph Engineering（图工程）重新设计 AI 的工作流**



## 正文

先问你一个工作中的真实问题：你的 Agent 出错时，你知道该改哪一层吗？

很多团队做 Agent，第一步是写 Prompt，第二步是接工具，第三步是上线，第四步开始不断打补丁。

你以为自己在优化 AI，实际上可能只是在给一个没有流程的系统补漏洞。

如果你也被“再调一下 Prompt”困住过，这篇文章说的就是你的工作日常。

这是一篇“AI 产品经理工作流”栏目文章。你可以把它当成一份检查清单：以后每次设计 Agent，先检查流程，再决定 Prompt 怎么写。

这一切通常从老板的一句话开始：给我们的产品接一个 Agent。

> 做一个智能助手，效果是用户问什么，它都能回答。
> 写一套 Skill 和 Markdown 文件不就够了吗？

上线以后，AI 有时像专家，有时像刚入行的实习生。用户说它答错了，你作为产品经理想优化，却不知道该改哪里：是 Prompt 有问题，还是工具没调对，还是整个流程从一开始就没设计清楚？

更麻烦的是，负责这个 Agent 的同事离职后，留下来的不是一套清晰的产品架构，而是一堆 Prompt、工具和补丁。后来的人只能继续打补丁，直到这个系统变成谁也不敢动的黑盒。

如果你也遇到过这些问题，问题可能不是 Prompt 和 Skill 不够多，而是团队把“写一套提示词”误认为“完成了产品设计”。

你把产品设计压缩成了一套 Prompt 和 Skill，才是 Agent 越调越乱的根因。

真正让人疲惫的，不是 AI 偶尔犯错，而是每次出错，你都不知道该改哪一层。

最近，一些 AI 工程实践开始用 Graph Engineering（图工程）来描述另一种工作方式：先设计工作流，再决定哪些环节交给 AI。

这个词听起来像技术名词，但对 AI 产品经理来说，真正重要的是它提供了一种解决方案：

> 在让 AI 开始干活之前，先把这件事应该怎么运转想清楚。

### Prompt 和 Skill 都写好了，为什么 Agent 还是越调越乱？

很多 AI 产品的设计，都是从“先把 Prompt 和 Skill 写出来”开始的。

团队会认真整理角色设定、行为规则、知识库和输出格式，甚至把各种异常情况也写进 Skill 里。这样做当然有价值，但它容易让人产生一种错觉：只要提示词足够完整，AI 就能自己把整个产品跑起来。

但一个真正能完成工作的系统，通常不只有“让 AI 回答”这一步。

用户的问题要不要先分类？

数据查不到怎么办？

工具调用失败要不要重试？

哪些事情可以让 AI 自己决定？

哪些操作必须经过用户确认？

如果答案不可靠，系统应该怎么兜底？

这些问题没有被设计清楚时，系统就只能把判断全部交给模型，再期待 Prompt 和 Skill 能覆盖所有情况。

于是，第一个问题出现了：你把产品设计压缩成了一套 Prompt 和 Skill。

它们可以规定 AI 的角色、语气、规则和任务目标，却不一定能替你定义每个步骤之间的关系。什么时候查数据，什么时候判断，什么时候调用工具，什么时候让用户确认，什么时候停止，都不能只靠一段越来越长的文字解决。

它既要理解用户意图，又要查资料、调用工具、做判断、生成答案，甚至还要执行有业务风险的动作。看起来是一个“全能助手”，实际上每个环节都可能出错，而且出了错也无法定位。

第二个问题是：出了问题，你不知道怎么改。

用户说“AI 回答错了”，你只能把对话复制给研发，再说一句：“帮忙优化一下。”研发可能改了 Prompt，这个问题暂时好了，另一个问题却出现了。

因为系统没有被拆开，你无法判断错误到底发生在：

- 客户资料没有查到；
- 客户阶段判断错了；
- AI 生成建议时出现了幻觉；
- 还是发送动作没有经过确认。

第三个问题是：接手产品之后无从下手。

当整个系统只有“输入—Prompt/Skill—模型—输出”这条模糊链路时，产品经理的工作就会慢慢变成继续调 Prompt、继续补 Skill。每次出问题，加一条规则；每次有新需求，再补一个例外。

时间久了，除了一开始接受的产品负责人知道系统为什么这样工作，也没人敢删掉旧逻辑。

这些问题可以归结为一句话：

> 你没有定义系统应该如何运转。

### Graph Engineering（图工程）如何把 Agent 的工作流程设计清楚

它不是要产品经理再记住一个流行词，而是在回答一个实际问题：怎样让 AI 更稳定地完成一项工作？

我们最终想做的事情很明确：利用大语言模型，替我们完成一些有用的工作。

但大语言模型不是传统意义上完全稳健、确定、可预测的软件。让它真正稳定地完成工作并不容易，所以我们不断尝试新的方法，而新的方法又形成了新的工程概念。

抛开术语，Graph Engineering（图工程）的意思可以用一句话说清楚：

> 先画好一张流程图，规定每一步该做什么、由谁来做、出错了怎么办，再决定哪些环节交给 AI。

把 AI 当成一个团队来管理，你会立刻看出问题。

一种方式是招一个“全能员工”，告诉他：“帮客户解决问题。”然后放手不管。这个员工有时能独立处理复杂问题，有时也会做出让人无法理解的决定。出了问题，你不知道他是在理解需求、查资料，还是执行动作时犯了错。

另一种方式是先把服务流程设计清楚：第一步接待客户，第二步判断需求，第三步分配处理，第四步确认结果，第五步完成交付。

简单、固定的步骤，让代码来执行；需要综合判断的步骤，交给 AI；可能带来风险的关键动作，必须经过校验或人工确认。

Graph Engineering（图工程）就是第二种方式。

以一个销售助手为例，你不会只告诉 AI：“帮我管理客户。”

你会先把工作拆开：

1. 查询客户资料：固定动作，读取数据库，不需要 AI 判断。
2. 判断客户阶段：需要结合沟通记录和行为信息分析，可以交给 AI。
3. 生成跟进建议：需要理解上下文并组织语言，可以交给 AI。
4. 发送邮件、更新系统：确定性动作，而且有业务风险，最好由代码执行，并在关键节点要求确认。

这四步连起来，就是一个基本的 Agent 工作流。

假设用户说：“把这个客户推进到签约阶段，并发一封跟进邮件。”

如果系统只有一个全能 Agent，它可能同时判断客户阶段、生成邮件、修改 CRM 状态，最后直接发出邮件。按照图工程拆分后，流程会先读取客户资料，再判断客户阶段，生成跟进建议，等待用户确认，最后更新 CRM 并发送邮件。

两种方式的差别，不是 Prompt 长短，而是有没有把高风险动作从模型的自由发挥中拿出来。

这也是这篇文章最想说的一句话：不要把一个团队的工作流程，压缩成一个人的岗位说明书。

它的重点不在于画图，而在于你开始明确：哪些事情应该固定下来，哪些事情需要模型判断，每一步的输入和输出是什么，失败后应该怎么走，哪些动作不能让 AI 自己决定。

### 一个节点可以由代码、模型或 Agent 承担

在传统 Workflow 里，一个节点通常是一个固定动作：执行一段代码、调用一个 API，或者调用一次大模型完成分类、提取和格式转换。

但现在，一个完整的 Agent 也可以作为图中的一个节点存在。

也就是说，一个节点可能是：

- **代码节点**：执行确定性的规则、数据查询或系统操作；
- **API 调用节点**：调用外部服务，获取数据或执行动作；
- **LLM 调用节点**：用一次模型调用完成分类、提取或生成；
- **Agent 节点**：把一个有自己工具、上下文和内部循环的完整 Agent，作为一个更大的工作流中的一环。

比如，一个知识库助手的整体流程可以是：先由代码或一次模型调用判断用户要查什么，再分别交给 GitHub Agent、Notion Agent 或 Slack Agent 去搜索，最后由一个汇总节点整理结果。

这里的 GitHub Agent、Notion Agent 和 Slack Agent，不是几段简单的 Prompt，而是可以独立规划、调用工具、反复检索并完成任务的 Agent。它们被放进更大的图里，外层流程负责规定什么时候调用、调用后去哪一步；Agent 内部则负责完成自己那一段更开放的工作。

这意味着，产品经理设计的不是“一个 AI 从头做到尾”，而是不同能力单元之间的组合：

> 固定的事情交给代码，简单判断交给一次模型调用，需要开放式解决的问题交给 Agent，流程则负责把它们连接起来。

#### 节点可以灵活组合，不等于把 Agent 变成死流程

如果每一步都提前规定好，Agent 还算智能吗？

答案是，Graph Engineering（图工程）并不是把所有决策都写死，而是把确定的部分固定下来，把需要判断的部分留给 AI。

真实的 Agent 工作流也不是一条从头走到尾的直线。它可能需要重试失败的工具调用，等待用户补充信息，经过校验后重新生成答案，也可能在关键节点暂停，等待人工确认。

所以，好的系统不是“全自动”，也不是“全手工”，而是让代码处理确定性，让 AI 处理复杂判断，让流程负责边界和协作。

这也是 LangGraph 这类图框架试图解决的问题：在确定性的流程路径和 Agent 的自主判断之间取得平衡。LangChain 团队在相关实践总结中提到，LangGraph 已被初创公司和大型企业使用。具体下载量应以原文最新数据为准。

所以，产品经理要设计的不是一条把 AI 锁死的流水线，而是一套有边界、又允许节点内部自主完成工作的系统。

### 这套方法会改变 AI 产品经理的三项工作

#### 1. 需求不再只有一句“让 AI 做判断”

以前的需求可能是：

> 用户输入问题，系统路由到对应的 Skill，分析后给出建议。

研发接着会问：分析失败了怎么办？建议需要用户确认吗？数据查不到怎么办？

这些问题不是研发在故意为难你，而是需求本身还没有被设计完整。

用 Graph Engineering（图工程）思维，你会在需求阶段就定义清楚：每一步由代码还是 AI 完成，输入是什么，输出是什么，错误怎么处理，哪些地方需要用户介入。

研发拿到的就不再是一句模糊的“做一个智能助手”，而是一套可以讨论、实现和验收的系统行为。

#### 2. 问题可以被定位到具体环节

用户再说“AI 答错了”时，你不必只能把问题转给研发。

你可以沿着流程去看：客户信息没有拉到，是资料查询节点的问题；把初步接触的客户判断成了商机，是客户阶段分析节点的问题；前面信息都正确但建议不合适，是方案生成节点的问题；建议没问题却未经确认就发出去了，是执行和权限控制的问题。

当问题被定位到具体节点，优化就不再是“再调一调 Prompt”，而是可以进一步讨论数据、规则、模型、流程和权限。

系统从一个黑盒，变成了一条可以逐段检查的路径。

#### 3. 验收不再只靠“感觉还不错”

缺少评测标准的验收，常见的说法是：“感觉有时候不太准。”

但“感觉”无法告诉团队应该改什么，也无法判断下一版到底有没有变好。

Graph Engineering（图工程）思维会让你把评测拆开：流程有没有完成，关键步骤有没有遗漏；每个节点的判断是否准确；数据查不到时，系统是否正确兜底；AI 有没有执行不该执行的动作；高风险操作是否经过用户确认。

这样一来，产品验收就从“整体感觉不错”，变成了有流程完成率、节点准确率和边界安全性的具体标准。

AI 产品也从“能不能回答”，走向“能不能稳定地完成一项工作”。

### 设计 Agent 前，先回答这五个问题

如果你正在设计一个 Agent 产品，先不要急着写 Prompt。先回答五个问题：

1. 用户最终想完成的业务动作是什么？不要只写“获得答案”。
2. 从输入到结果，中间必须经过哪些步骤？
3. 每一步由谁来做：代码、单次模型调用、完整 Agent，还是人工？
4. 每一步的输入、输出和失败处理是什么？
5. 哪些地方必须评测，哪些动作必须确认？

写完之后，再回头决定 Prompt 怎么写、工具怎么接、模型用哪个。

你会发现，Prompt 只是系统中的一个节点，而不是整个产品。

建议把这五个问题保存下来，放进你的 Agent 需求模板。每次评审需求时，逐项检查，不要等上线后才开始补流程。

### 我把这套方法做成了一个 AI 产品经理 Skill

理解 Graph Engineering（图工程）之后，我把这套思路写成了一个 AI 产品经理 PRD 构建 Skill。

它不是简单生成一套 Prompt，而是通过多轮对话，把一个模糊的产品想法逐步拆成一份可讨论、可实现、可评测的 PRD：

1. 先确认业务背景、目标和真实流程；
2. 再判断每个环节适合用代码、单次模型调用还是 Agent；
3. 逐个定义 AI 节点的输入、输出、行为边界和异常处理；
4. 根据节点复杂度讨论模型和 Prompt 策略；
5. 在需求阶段提前设计评测维度、测试数据和验收标准。

这样一来，Skill 覆盖的就不只是“AI 应该怎么说”，而是“这个 Agent 应该怎么工作”。它同时帮产品经理处理产品流程、系统节点、PRD 编写和评测设计，避免项目做到最后才发现：流程没定义，边界没写清楚，效果也不知道怎么验收。

当然，一个 Skill 不能替产品经理做完所有判断。它真正能做的，是把那些经常被遗漏、但又决定 Agent 是否可用的问题，变成一套可以反复检查的工作流程。

## 结尾：先设计工作，再决定 AI 如何参与

Graph Engineering（图工程）不是一个新技术，也不只是 AI 时代又一个听起来漂亮的流行词。

它提醒产品经理回到一个朴素的道理：

> 在让 AI 做事情之前，你得先想清楚这件事本来应该怎么做。

这正是产品经理应该承担的工作：先定义问题和流程，再决定 AI 如何参与。

下一次有人说“先接一个 Agent，再慢慢调 Prompt”，你可以先追问一句：

> 这个 Agent 要完成的工作，具体经过哪些步骤？

如果你正在设计 Agent，欢迎把最容易出错的环节记下来：是资料查询、模型判断、工具调用，还是用户确认？这个问题的答案，通常就是下一轮产品设计的起点。
