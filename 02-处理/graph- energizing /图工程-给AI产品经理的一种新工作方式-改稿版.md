# Agent 越调越乱，问题可能不在 Prompt：给 AI 产品经理的 graph-engineering 工作法

> 你不需要再写一条 Prompt，而是需要先把这件事应该怎么完成想清楚。

如果你负责过 Agent，下面这个场景大概率并不陌生。

老板说：“给我们的产品接一个智能助手。”

于是你们开始写 Prompt、整理 Skill、接知识库、配工具。第一版上线后，AI 有时像专家，有时像刚入行的实习生。用户说：“它答错了。”大家又开始补规则、改提示词、加例外。

改完一个问题，新的问题马上出现：资料查错了、客户阶段判断错了、邮件写得不错却直接发出去了。负责项目的人离职后，留下来的不是一套清晰的产品设计，而是一堆没人敢删的 Prompt、工具和补丁。

你以为自己在优化 AI，实际上可能只是在给一个没有流程的系统补漏洞。

这篇文章想解决的，就是 AI 产品经理最疲惫的那个问题：

> 每次 Agent 出错，我到底应该改 Prompt、改工具，还是重做流程？

答案是：先别急着改 Prompt。先用 graph-engineering 的方式，把 Agent 的工作流程设计清楚。

## 你把产品设计压缩成了一套 Prompt

很多 Agent 项目都从“先把 Prompt 和 Skill 写出来”开始。

团队会认真写角色设定、行为规则、知识库和输出格式，也会把各种异常情况补进 Skill。这样做当然有用，但很容易产生一个错觉：只要提示词足够完整，AI 就能自己把整个产品跑起来。

可一个真正能完成工作的系统，通常不只有“让 AI 回答”这一步。

用户的问题要不要先分类？

数据查不到怎么办？

工具调用失败要不要重试？

哪些事情可以让 AI 自己决定？

哪些操作必须经过用户确认？

如果答案不可靠，系统应该怎样兜底？

这些问题没有被设计清楚时，系统只能把判断全部交给模型，再期待一段越来越长的文字覆盖所有情况。

于是，问题就出现了。

第一，Prompt 和 Skill 能规定 AI 的角色、语气和任务目标，却不一定能定义步骤之间的关系。什么时候查数据，什么时候判断，什么时候调用工具，什么时候等待确认，什么时候停止，都不是单靠一段说明就能稳定解决的。

第二，出了问题，你不知道问题发生在哪一层。用户说“AI 回答错了”，你只能把对话复制给研发，再说一句：“帮忙优化一下。”研发改了 Prompt，这次看起来好了，另一个场景却坏了。

第三，产品无法交接。每次有新需求，就加一条规则；每次出现例外，就补一个条件。时间久了，没人知道旧逻辑为什么存在，也没人敢动它。

真正让人疲惫的，不是 AI 偶尔犯错，而是每次犯错，你都不知道该改哪里。

## graph-engineering 到底在解决什么

graph-engineering 听起来像一个技术名词，但对产品经理来说，可以先把它理解成一句很朴素的话：

> 先画清楚工作流程，规定每一步做什么、由谁来做、失败了怎么办，再决定哪些环节交给 AI。

把 AI 当成一个团队来管理，你会更容易理解这件事。

一种做法是招一个“全能员工”，只告诉他：“帮客户解决问题。”他有时能独立处理复杂任务，有时也会做出无法解释的决定。出了问题，你不知道他是在理解需求、查资料，还是执行动作时犯了错。

另一种做法是先把服务流程拆开：第一步接待客户，第二步判断需求，第三步查找资料，第四步生成方案，第五步确认结果，第六步完成交付。

固定、简单、可预测的事情交给代码；需要理解上下文和综合判断的事情交给 AI；有业务风险的关键动作，经过校验或人工确认。

这就是 graph-engineering 的核心思路。

它关注的不是“画一张好看的图”，而是把一个模糊的“AI 助手”拆成一组可以讨论、实现、测试和交接的节点。

## 一个销售助手，应该怎样被拆开

比如，你要做一个销售助手。你不会只告诉 AI：“帮我管理客户。”

你会把它拆成四步：

1. 查询客户资料：读取数据库，是固定动作，不需要 AI 判断。
2. 判断客户阶段：结合沟通记录和行为信息分析，可以交给 AI。
3. 生成跟进建议：理解上下文、组织语言，可以交给 AI。
4. 更新 CRM、发送邮件：确定性动作且有业务风险，应该由代码执行，并在关键节点要求确认。

假设用户说：“把这个客户推进到签约阶段，并发一封跟进邮件。”

一个全能 Agent 可能会同时判断客户阶段、生成邮件、修改 CRM 状态，最后直接发出邮件。任何一个环节出错，结果都会变成一个难以追溯的整体错误。

按照 graph-engineering 拆分，系统会先读取客户资料，再判断客户阶段，生成跟进建议，等待用户确认，最后更新 CRM 并发送邮件。

两种方式的差别，不是 Prompt 长短，而是有没有把高风险动作从模型的自由发挥中拿出来。

这句话值得转给那个总在说“再补一条 Prompt 就好了”的同事：

> 不要把一个团队的工作流程，压缩成一个人的岗位说明书。

## 一个节点，不只可以是一次模型调用

在传统 Workflow 里，一个节点通常是代码、API 或一次模型调用。但在更复杂的 Agent 系统里，一个完整的 Agent 也可以作为图中的一个节点。

因此，一个节点可能由四种角色承担：

- 代码节点：执行规则、查询数据或操作系统；
- API 节点：调用外部服务获取数据或完成动作；
- LLM 节点：完成分类、提取、改写等单次任务；
- Agent 节点：使用自己的工具、上下文和内部循环，完成一段更开放的工作。

例如，一个知识库助手可以先由代码或一次模型调用判断用户要查什么，再分别交给 GitHub Agent、Notion Agent 或 Slack Agent 搜索，最后由汇总节点整理结果。

外层流程负责规定什么时候调用、调用后去哪一步；Agent 内部负责完成自己那一段需要探索的工作。

这并不意味着所有步骤都要被写死。好的系统不是“全自动”，也不是“全手工”，而是让代码处理确定性，让 AI 处理复杂判断，让流程负责边界和协作。

它可以重试失败的工具调用，可以等待用户补充信息，可以在校验后重新生成答案，也可以在关键节点暂停，等待人工确认。

灵活性应该发生在节点内部，而不是让整个系统失去边界。

## 这套方法会改变 AI 产品经理的三项工作

### 1. 需求从一句话变成一套可执行的流程

“用户输入问题，系统路由到对应 Skill，分析后给出建议”，这不是完整需求，只是一个愿望。

用 graph-engineering 思维，你需要继续回答：每一步由谁完成？输入和输出是什么？失败后往哪里走？哪些地方需要用户介入？

研发拿到的就不再是一句模糊的“做一个智能助手”，而是一套可以实现和验收的系统行为。

### 2. 问题可以定位到具体节点

用户再说“AI 答错了”时，你可以沿着流程检查：

- 客户信息没有拉到，是资料查询节点的问题；
- 客户阶段判断错了，是分析节点的问题；
- 前面信息都正确但建议不合适，是生成节点的问题；
- 建议没问题却未经确认就发出去了，是执行和权限控制的问题。

当错误能被定位，优化就不再是“再调一调 Prompt”，而是具体讨论数据、规则、模型、流程和权限。

### 3. 验收从“感觉还不错”变成可衡量的标准

“这个 Agent 有时候不太准”无法指导团队改进，也无法判断下一版到底有没有变好。

你可以把评测拆成几层：流程有没有完成，关键步骤有没有遗漏；每个节点的判断是否准确；数据查不到时是否正确兜底；AI 有没有执行不该执行的动作；高风险操作是否经过确认。

AI 产品也就从“能不能回答”，走向“能不能稳定地完成一项工作”。

## 设计 Agent 前，先问自己五个问题

下次再接到“给产品加一个 Agent”的需求，先不要打开 Prompt 编辑器。把下面五个问题写进需求模板：

1. 用户最终要完成的业务动作是什么？不要只写“获得答案”。
2. 从输入到结果，中间必须经过哪些步骤？
3. 每一步由谁完成：代码、单次模型调用、完整 Agent，还是人工？
4. 每一步的输入、输出和失败处理是什么？
5. 哪些地方必须评测，哪些动作必须确认？

回答完，再决定 Prompt 怎么写、工具怎么接、模型用哪个。

你会发现，Prompt 只是系统中的一个节点，而不是整个产品。

这五个问题的价值在于，它们不依赖某个模型或框架。换一套工具、换一个业务场景，仍然可以用来检查需求是否完整。

如果你只保存一段话，建议保存这一段：

> 业务目标 → 流程节点 → 执行角色 → 异常处理 → 评测标准

这条链路，才是 AI 产品从“能演示”走向“能交付”的关键。

## 我把这套方法做成了一个 AI 产品经理 Skill

如果你不想每次都从空白文档开始，我把上面的思路整理成了一个 AI 产品经理 PRD 构建 Skill。

它不是简单帮你生成一套 Prompt，而是通过多轮对话，把一个模糊想法逐步拆成一份可讨论、可实现、可评测的 PRD：

1. 确认业务背景、目标和真实流程；
2. 判断每个环节适合用代码、单次模型调用还是 Agent；
3. 定义 AI 节点的输入、输出、行为边界和异常处理；
4. 根据节点复杂度讨论模型和 Prompt 策略；
5. 提前设计评测维度、测试数据和验收标准。

它解决的不是“AI 应该怎么说”，而是“这个 Agent 应该怎么工作”。

当然，一个 Skill 不能替产品经理完成所有判断。它真正能做的，是把那些经常被遗漏、却决定 Agent 是否可用的问题，变成一套可以反复检查的工作流程。

如果你正在做 Agent，可以先用一个真实需求试一遍：把原来的“功能描述”改写成“业务目标—流程节点—执行角色—异常处理—评测标准”。哪怕暂时不用这个 Skill，你也会更快看出需求里缺了什么。

## 结尾：先设计工作，再决定 AI 如何参与

graph-engineering 不是又一个需要背下来的流行词。

它只是提醒我们回到一个朴素的产品原则：

> 在让 AI 做事情之前，先想清楚这件事本来应该怎么做。

下一次有人说“先接一个 Agent，再慢慢调 Prompt”，你可以先追问一句：

> 这个 Agent 要完成的工作，具体经过哪些步骤？

如果你正在做 Agent，评论区可以聊聊：你现在最容易卡在哪一步？

- A：需求说不清，不知道 Agent 到底要完成什么
- B：流程拆不开，所有事情都交给一个 Agent
- C：效果不稳定，出了问题不知道该改哪里
- D：上线难验收，不知道怎样判断它真的变好了

你选的那一项，往往就是最值得先画清楚的那张流程图。

如果这篇文章帮你重新看清了 Agent 的问题，可以先收藏下来，下一次评审需求时逐项检查；也可以转发给正在不断补 Prompt 的同事。

关注“AI native 产品经理 ”栏目，后续会继续把需求、节点、评测和交付拆开讲清楚。
