# 从零到一：一个写作 Agent 的 Harness 工程迭代

**建议阅读人群**：产品经理 / 对 Agent Harness 感兴趣的非纯技术人员

**Demo 场景**：开发一个"写作 Agent"。用户提供写作主题和风格参考文章，Agent 联网调研后，在指定路径下输出文稿。

**核心思路**：以写作 Agent 为例，演示如何从一个"出厂配置"的基础 Agent 描述，逐层叠加 Harness 策略，最终形成一份可靠的开发规格。每一层都解决上一层暴露的问题，循环渐进。

此文档由 MiMo-2.5-Pro 驱动的 Hermes 协助撰写，感谢 MiMo 100t 计划。

## 第零章：需求背景

### 用户是谁？

一位内容创作者。

他想写一篇关于某个主题的深度文章，手头有几篇风格参考文章，希望 AI 帮他完成：

```
调研 → 构思 → 撰写 → 修改
```

最终在指定文件夹里输出成品。

### 我们要造什么？

一个写作 Agent。

它具备以下工具：

| 工具 | 用途 |
|---|---|
| `bash` | 执行 shell 命令，用于联网搜索、文件系统操作等 |
| `read_file` | 读取文件内容 |
| `write_file` | 写入文件 |
| `edit_file` | 编辑已有文件 |
| `web_search` | 联网搜索 |

**用户输入**：

```
写作主题 + 风格参考文章路径 + 输出路径
```

Agent 在输出路径下生成最终文稿。

**交互方式**：

- 用户在对话界面输入："帮我写一篇关于 XX 的文章，风格参考见 XX 文件，输出到 XX 目录"
- Agent 执行过程中，用户可以查看当前进度，也可以中途追加指示
- 任务完成后，Agent 告知用户文稿路径

### 为什么用这个场景拆解？

写作任务天然是一条链路：

```
调研 → 大纲 → 初稿 → 润色
```

步骤明确但不琐碎，适合展示 Agent 如何规划、如何执行、如何从错误中恢复。

它不需要复杂的代码工具链，也方便产品经理理解每一个 Harness 环节的意义。

## 第一章：出厂配置 —— 最基础的 Agent 描述

### 核心思路

一个 Agent 的最小构成是：

```
模型 + 循环 + 工具 = 一个能动的 Agent
```

可以理解为：

> 刚出厂的新 Agent，能打电话，但还没装 App。

它的基础流程是：

```
用户输入需求
    ↓
LLM 推理
    ↓
判断是否需要工具
    ↓
需要工具：调用工具 → 工具返回结果 → 继续推理
不需要工具：输出结果给用户
```

### 三个基本要素

1. **循环 Loop**
   接收需求 → 推理 → 调用工具 → 拿到结果 → 继续推理，直到模型判断任务完成。

2. **工具 Tools**
   让模型能和真实世界交互，比如读写文件、搜索网页。

3. **规划 Planning**
   让模型在动手前先想清楚："我要分几步做？"

### V0.1 描述

核心要求：

- 用户输入写作主题、风格参考文章路径、输出路径
- Agent 联网调研
- 读取参考文章
- 生成文章
- 写入指定输出路径
- 完成后告知用户文稿路径

具体来说，基于 LLM API 实现一个 Agent 循环：接收用户需求 → 模型推理 → 决定是否调用工具 → 调用工具 → 拿到结果 → 继续推理，直到模型判断任务完成。提供 `bash`、`read_file`、`write_file`、`edit_file`、`web_search` 五种工具。每轮循环中，模型自行决定下一步是搜索资料、阅读参考文章、撰写文稿还是编辑修改。

### 这个描述能跑吗？

能跑，但问题很多：

- Agent 做了 20 条搜索结果后，上下文直接膨胀，后面什么都看不清。
- 写到一半跑偏，开始写无关内容。
- 中途断了，也不知道该继续哪一步。
- Agent 觉得自己写完了，其实只是写了个开头或大纲。

### Agent 怎么知道"我做到哪一步了"？

它不知道。

因为我们的产品描述里只定义了"Agent 需要做哪些事"，但没有定义"做到哪了、下一步是什么、什么时候算完成"。

一个没有任务清单的 Agent，就像一个没有清单的实习生。

## 第二章：任务规划与状态管理 —— 让 Agent 知道自己在干嘛

### 上一轮的问题

V0.1 的 Agent 有两个致命缺陷：

1. **没有任务清单**
   模型不知道自己完成了什么、还剩什么。在长任务里，前面的事会被后面的信息挤出注意力，导致重复干活或遗漏步骤。

2. **没有"完成"的判断标准**
   模型无法稳定判断任务是否真的结束。有时任务没完成就停了，有时已经完成还在乱搜。

### Harness 策略

#### 策略一：强制任务规划 TodoWrite

在循环开始前，要求 Agent 先生成一份结构化任务清单。

这份清单会作为上下文的一部分，在每一轮循环中持续显式提醒模型。

流程：

```
用户输入需求
    ↓
理解提示词
    ↓
LLM 生成任务清单
    ↓
进入循环
    ↓
LLM 推理下一步
```

任务计划以 markdown 文件的形式保存在输出路径下（`plan.md`），包含步骤清单和当前状态。计划中每一步是一个 checkbox 项，格式如 `- [ ] 步骤描述`。完成的步骤标记为 `- [x]`。计划还包含一个"当前状态"区域，标注当前执行到第几步、备注信息等。

#### 策略二：状态追踪与进度回顾

通过 Hooks 或状态文件，在每轮循环结束时，自动把任务清单重新拼接到上下文中。

Agent 每完成一个步骤，必须先更新 plan.md（打勾 + 更新当前状态），再继续下一步。

这样越靠后的上下文越能提醒模型：

```
我做到哪了
还有什么没做
当前步骤是否完成
```

当所有步骤都打勾后，Agent 做一次最终检查，确认文稿已写入输出路径，然后结束任务。

#### 策略三：熔断机制

设置最大循环轮次，例如 50 轮。

如果连续多轮没有更新任务状态，说明 Agent 可能已经陷入重复或跑偏，需要强制进入提示用户或结束流程。超过 50 轮强制停止，输出当前已有成果。

### V0.2 描述

新增能力：

- Agent 必须先生成任务清单
- 每一项任务都有状态
- 每轮执行后必须更新状态
- 如果当前步骤无法推进，要说明原因
- 如果需要用户补充信息，要暂停并提问
- 超过最大循环轮次时，要输出当前已有成果和未完成项

### 这样就好了吗？

好了不少。

Agent 现在有清单了，知道自己做到哪了，也有了"完成"的判断标准。

但新问题来了：

- 写作任务需要大量资料，参考文章可能很长。
- 搜索结果很多，上下文很快爆掉。
- Agent 读了参考文章、搜索结果、任务清单后，容易忘记最初目标。
- 写出来的东西可能越来越像"营销软文"，而不是用户要的风格。

于是进入下一层：上下文管理。

## 第三章：上下文管理 —— 在有限空间里"无限"工作

### 上一轮的问题

上下文窗口就像一个工作台，空间有限。

例如：

- 一个 1000 行的文件可能是 4000 tokens。
- 搜索结果可能有几万 tokens。
- 参考文章 + 多轮搜索 + 工具结果，很容易超过上下文上限。

如果不管理，上下文会把任务拖垮。

### Harness 策略

#### 策略一：首轮上下文精准组装

不是把所有信息都塞进去，而是分层组装：

| 内容 | 何时注入 | Token 成本 |
|---|---|---|
| 系统角色 + 工具说明 | 每次请求都带 | 固定开销 |
| 任务清单 `plan.md` | 每次请求都带 | 小 |
| 技能说明摘要 | 首次注入且保留摘要 | 小 |
| 技能知识全文 | 模型主动请求时才注入 | 按需 |
| 用户资料信息 | 自动拼接 | 小 |

#### 策略二：消息历史滚动压缩

每轮工具调用结果不全部保留在上下文中。

当 Agent 的消息历史接近上下文窗口的 70% 时，系统自动触发压缩。调用一个独立的 LLM 请求，将早期对话轮次压缩为摘要，替换原始消息。

压缩后的摘要中保留：关键结论、决策理由、文件路径引用。

丢弃：搜索结果原文、中间推理过程、已归档文件的完整内容。

被压缩的原始内容写入输出路径下的 `.archive/` 目录，Agent 需要时可以重新读取。

#### 策略三：Subagent 分派

长任务交给 Subagent。

例如搜索和资料整理：

```
主 Agent：只收到简短摘要
Subagent：负责完整搜索和分析
```

搜索环节支持派生子 Agent，主 Agent 发出搜索指令，Subagent 在独立的上下文中执行搜索、筛选，只返回结论摘要给主 Agent。

好处是主 Agent 的上下文不会被搜索结果撑爆。10 条搜索 × 每条 3000 字的原始结果，压缩为 10 条 × 每条 50 字的摘要，主 Agent 上下文占用从 30000 字降到 500 字。

#### 策略四：Skills 按需加载

如果 Agent 有很多技能，例如：

- 写作技能
- 公文写作
- 商业文案
- 论文写作

不要一开始全塞进去。

系统提示词中只放技能目录（名称 + 一句话描述）。当模型判断需要某种技能时，通过工具调用加载该技能的完整说明，注入当前上下文。

### V0.3 描述

新增能力：

- 当上下文超过阈值（70%）时，必须压缩。
- 只保留任务目标、关键结论、决策理由、已完成操作和工具摘要。
- 长网页、长文章、完整搜索结果放到 `.archive/` 目录。
- Agent 每完成一个步骤，将该步骤的工作记录写入 `work_log.md`。后续步骤需要回顾之前的结果时，从 work_log 读取，而不是依赖对话历史中的原始内容。
- 需要广泛搜索、多源对比时，使用 Subagent。Subagent 独立完成搜索，只返回压缩摘要。

### 上下文管理好了，然后呢？

新的问题出现了：

Agent 会执行 `bash` 命令，会写文件，会编辑文件。
如果它执行危险命令怎么办？
如果它把重要文件覆盖了怎么办？
如果它写到不该写的目录怎么办？

于是进入第四层：沙箱与权限管理。

## 第四章：沙箱与权限管理 —— 给 Agent 画一个安全围栏

### 上一轮的问题

Agent 能执行：

```
bash
write_file
edit_file
```

这就带来风险：

- 误删文件
- 覆盖重要文件
- 写到错误目录
- 执行危险命令
- 访问不该访问的路径

这不是 Agent 不聪明，而是你没有给它边界。

### Harness 策略

#### 策略一：工作空间沙箱

为 Agent 定义一个工作空间。

所有文件操作都必须发生在这个目录内。工作空间即输出路径，Agent 启动时自动确认该路径存在且可写。

流程：

```
Agent 请求文件路径
    ↓
解析为绝对路径
    ↓
判断是否在工作空间内
    ↓
是：允许执行
否：拒绝，并告诉 Agent 越界
```

系统在每次执行文件操作前，自动将路径解析为绝对路径并校验是否在工作空间内，越界则拒绝执行并返回错误信息给 Agent。

#### 策略二：命令分层权限

把命令分成三类：

| 类型 | 说明 | 示例 |
|---|---|---|
| 白名单 | 可直接执行 | `ls`、`cat`、`mkdir`、`grep`、`head`、`tail`、`wc`、`pwd` |
| 需确认 | 有风险，需要用户确认 | `curl`、`wget`（下载外部资源）、`rm`（删除文件）、`mv`（移动文件） |
| 黑名单 | 永远禁止 | `rm -rf /`、`chmod 777`、`sudo`、任何涉及系统目录的操作 |

#### 策略三：路径逃逸防护

如果 Agent 写：

```
../../secret.txt
```

系统必须先规范化为绝对路径（resolve），再检查它是否仍在工作区内。

Agent 在多次目录跳转中可能拼接出 `../../` 这样的路径意外逃出工作空间。系统在每次文件操作前，将路径规范化后再做校验。

如果不在，就拒绝。

#### 策略四：联网内容管理

联网下载的内容（如搜索结果、网页正文）必须保存到输出路径下的 `sources/` 子目录，不得写入其他位置。

### V0.4 描述

新增能力：

- Agent 只能在指定 workspace/output 目录内操作。
- 写入、编辑、删除文件前必须检查路径。
- 超出工作空间时拒绝执行，并提示用户。
- 对命令进行分级权限管理。
- 对不明确路径，要求用户确认。

### 安全问题解决了，但还有个效率问题

如果每个文件操作、每个命令都要模型自己记得检查，效率很低。

如果每次都要手动确认，自动化也会被打断。

于是进入第五层：Hooks。

## 第五章：Hooks —— 不需要模型操心的自动化

### 上一轮的问题

我们把路径、权限、安全规则都写进提示词后，提示词越来越长。

Agent 每次都要"记得"检查路径、检查权限、更新日志。

但这些机械操作，本来就不应该浪费模型注意力。

### Harness 策略

Hooks 是系统在某个时机自动执行的固定动作。它不需要模型主动想起来。在 Agent 循环的关键节点，插入自动执行的脚本（Hooks），不经过模型推理，由程序直接执行。

常见 Hooks：

| Hook | 触发时机 | 做什么 |
|---|---|---|
| `pre_tool_use` | 工具调用前 | 检查路径、权限、命令是否安全 |
| `post_tool_use` | 工具执行后 | 记录日志、抽取摘要、更新状态 |
| `on_write_file` | 写文件成功后 | 自动保存快照 |
| `on_loop_end` | 每轮结束后 | 检查是否超时、重复、无进展 |
| `on_error` | 工具失败时 | 结构化错误，决定重试或降级 |

#### 执行前 Hooks（工具调用之前触发）

- **路径校验 Hook**：对所有文件操作的路径参数做安全校验（解析绝对路径 → 检查是否在工作空间内 → 越界则拦截并返回错误）。
- **JSON 格式校验 Hook**：检查模型生成的工具调用参数格式是否正确（如缺少引号、括号不匹配等），可自动修复的就修复，修复不了的才回传给模型重新生成。

#### 执行后 Hooks（工具调用之后触发）

- **任务状态注入 Hook**：每轮循环结束时，自动读取 plan.md 的最新内容，拼接到消息列表末尾。利用近因效应确保模型每轮都能看到"我做到哪了"。
- **工作日志 Hook**：每次 `write_file` / `edit_file` 执行成功后，自动将文件变更记录追加到 `work_log.md`。
- **进度监控 Hook**：每轮循环结束时，检查 plan.md 的最后更新时间。如果连续 3 轮未更新，向消息列表注入一条提醒："你已经 3 轮没有更新任务计划了，请审视当前进度。"
- **上下文压缩 Hook**：每轮循环结束时，检查消息总长度。超过上下文窗口的 70% 时，自动触发上下文压缩流程。

### V0.5 描述

新增能力：

- 每次工具调用前，自动执行安全 Hook。
- 检查路径、命令、权限。
- 每次工具调用后，记录工具名、参数、结果摘要。
- 写文件或编辑文件成功后，自动保存快照。
- 工具失败时，记录失败原因和影响范围。

### Hooks 是万能的吗？

不是。

Hooks 只能做固定动作。

它能检查路径是否越界。
它能记录工具调用日志。
它能保存快照。

但它不能判断文章写得好不好，方案方向对不对，用户是否满意。

于是进入第六层：记忆。

## 第六章：记忆管理 —— 让 Agent 越用越熟

### 上一轮的问题

Agent 每次启动都像新人。

它不知道：

- 用户喜欢什么风格
- 之前犯过什么错
- 项目里有哪些约定
- 哪些资料已经验证过
- 哪些做法不要再重复

### Harness 策略

#### 策略一：自动记忆提取

每次任务结束后，系统自动调用 LLM，从过程中提取可复用信息：

- **用户偏好**
  例如：喜欢短句、少比喻、不要太营销。

- **项目规则**
  例如：输出文稿必须保存到指定目录。

- **错误教训**
  例如：不要只看前三个搜索结果。

提取结果以结构化文本存储。提取内容包括：用户偏好的写作风格、常写主题、被纠正过的写作习惯、常用输出路径等。

#### 策略二：跨会话检索

下一次任务开始前，先检索相关记忆，并注入上下文。

每次新会话开始时，系统自动将用户记忆摘要注入到首轮上下文的系统提示词区域。让 Agent 在规划之前先知道：

```
这个用户以前有什么偏好？
这个项目有哪些固定规则？
上次哪里出过错？
```

Agent 在写作过程中应遵循这些偏好，但如果用户在本次对话中给出冲突指示，以本次为准。

每次任务结束后，新的提取结果与已有记忆合并（去重、更新、淘汰过时信息）。

当用户在新会话中提到"上次写的那篇 XX""之前我们讨论过的 XX"等涉及历史会话的内容时，Agent 可通过关键词检索历史会话记录。检索结果不是全量加载，而是只拉取与关键词相关的片段摘要，注入当前上下文。

### V0.6 描述

新增能力：

- 任务开始前检索相关记忆。
- 任务执行中如果发现稳定偏好、项目规则、错误教训，就写入记忆。
- 只保存可复用、稳定的信息。
- 不保存一次性临时信息。

### 记忆有了，但还有个大问题

如果工具调用失败了怎么办？

例如：

- 搜索 API 超时
- `write_file` 写入失败
- `read_file` 读到乱码
- `web_search` 返回无关信息

如果没有错误恢复，Agent 可能会反复重试，或者把错误信息塞进上下文，然后越来越乱。

于是进入第七层：错误恢复。

---

## 第七章：错误恢复 —— 小错不崩，大错可控

### 上一轮的问题

没有错误恢复机制时：

- API 超时后，Agent 不知道该怎么办，只会重复试。
- `write_file` 失败后，Agent 可能不知道文件是否已经写入。
- 多次失败后，上下文被错误信息污染，任务目标被淹没。

### Harness 策略

#### 策略一：错误信息结构化处理

工具失败时，不是把原始报错直接塞进上下文。

而是结构化成：

```
工具调用失败：web_search
原因：API 请求超时
现象：搜索结果为空
这次结论：没有获得有效信息，不能作为依据
建议下一步：更换关键词或稍后重试
```

系统自动将错误处理为结构化摘要，包含：失败的工具名、失败原因（超时/权限/格式等）、建议的下一步操作（重试/换策略/跳过）。结构化错误信息比一堆 stack trace 对模型友好得多，模型看到后知道该怎么做。

#### 策略二：失败计数与降级

对每个工具的每次调用维护失败计数。

| 失败次数 | 策略 |
|---|---|
| 第 1 次 | 告知失败原因，将结构化错误信息返回给模型，让它自行决定是否重试 |
| 第 2 次 | 明确建议换工具、换查询词或跳过该步骤 |
| 第 3 次 | 强制跳过该步骤，在 `plan.md` 中标记"已跳过"并记录原因，继续执行后续步骤 |

#### 策略三：关键节点自动存档

每次 `write_file` 或 `edit_file` 成功后，自动保存快照（如通过 git commit 或文件备份）。

如果后续步骤把文稿改坏，可以回滚到上一个正常版本。

### V0.7 描述

新增能力：

- 工具调用失败时，结构化记录错误。
- 连续失败时，自动降级。
- 多次失败后，跳过当前步骤，并记录原因。
- 写文件成功后保存快照。
- 如果后续改坏，可以回滚。
- 如果系统判断任务已经卡死，应请求用户介入。

## 回到 DeepSeek 的公式

```
Model + Harness = Agent
```

这七层迭代展示了 Harness 到底在做什么：

- **循环**让模型能行动。
- **任务规划**让模型不迷路。
- **上下文管理**让模型不遗忘。
- **沙箱**让模型不越界。
- **Hooks**让机械操作不消耗模型注意力。
- **记忆**让模型能成长。
- **错误恢复**让模型不崩溃。

每一层都不是"锦上添花"，而是在真实场景中必须解决的工程问题。

跳过任何一层，Agent 在实际使用中都会暴露对应缺陷。

## 附录：给产品经理的自检清单

如果你正在设计一个 Agent 产品，可以逐项检查：

- [ ] **循环控制**：Agent 有明确的停止条件吗？最大轮次限制是多少？
- [ ] **任务规划**：Agent 能生成任务清单吗？清单会在每轮循环中被回顾吗？
- [ ] **状态管理**：Agent 怎么知道自己做到哪了？连续跑偏时有检测机制吗？
- [ ] **上下文窗口**：系统提示词占了多少 token？工具定义占了多少？给对话历史留了多少空间？
- [ ] **上下文压缩**：消息历史太长时怎么处理？压缩后关键信息丢了吗？
- [ ] **沙箱**：Agent 的文件操作有路径限制吗？能逃逸出工作空间吗？
- [ ] **权限管理**：哪些命令直接执行？哪些需要用户确认？哪些永远禁止？
- [ ] **Hooks**：哪些操作可以自动化？哪些不该依赖模型主动记得去做？
- [ ] **记忆**：用户偏好怎么跨会话传递？历史会话怎么检索？
- [ ] **错误处理**：工具调用失败时怎么告诉模型？连续失败时怎么降级？
- [ ] **用户追加消息**：Agent 干活时用户发了新消息，怎么处理？中断还是排队？
