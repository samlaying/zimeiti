## 开头

**建议阅读人群**：产品经理 / 对 Agent Harness 感兴趣的非纯技术人员

**Demo 场景**：开发一个「写作 Agent」：用户提供写作主题和风格参考文章，Agent 联网调研后在指定路径下输出文稿。

**核心思路**：以写作 Agent 为例，演示如何从一个「出厂配置」的基本 Agent 描述，逐层叠加 Harness 策略，最终形成一份可靠的开发规格。每一层都解决上一层暴露的问题，循序渐进。

## 第零章：需求背景

### 用户是谁？

一位内容创作者。他想写一篇关于某个主题的深度文章，手头有几篇风格参考文章，希望 AI 帮他完成「调研 -> 构思 -> 撰写 -> 修改」的全流程，最终在指定文件夹里输出成品。

### 我们要造什么？

一个写作 Agent。它具备以下工具：

| 工具 | 用途 |
|---|---|
| `bash` | 执行 shell 命令，用于联网搜索、文件系统操作等 |
| `read_file` | 读取文件内容 |
| `write_file` | 写入文件 |
| `edit_file` | 编辑已有文件 |
| `web_search` | 联网搜索 |

用户输入：写作主题 + 风格参考文章（文件路径）+ 输出路径。

Agent 在输出路径下生成最终文稿。

### 为什么要用这个场景拆解？

写作任务有一个好特性：它天然是一条链路（调研 -> 大纲 -> 初稿 -> 润色），步骤明确但不琐碎，适合展示 Agent 如何规划、如何执行、如何从错误中恢复。而且它不需要复杂的代码工具链，方便产品经理理解每一个 Harness 环节的意图。

## V0.1 描述：出厂配置

```Markdown
我要开发一个「写作 Agent」产品。需求如下：

产品功能：用户通过对话框输入写作主题，上传风格参考文章（或提供文件路径），指定输出路径。Agent 自主完成从调研到成稿的全流程，最终在输出路径下生成文稿。

## 交互方式：
- 用户在对话界面输入：「帮我写一篇关于 XX 的文章，风格参考见 XX 文件，输出到 XX 目录」。
- Agent 执行过程中，用户可以查看当前进度（如有 UI），也可以中途追加指示。
- 任务完成后，Agent 告知用户文稿路径。

## 技术方案：
- 基于 LLM API，实现一个 Agent 循环：接收用户需求 -> 模型推理 -> 决定是否调用工具 -> 调用工具 -> 拿到结果 -> 继续推理，直到模型判断任务完成。
- 提供以下工具供模型调用：`bash`（执行 shell 命令）、`read_file`（读取文件）、`write_file`（写入文件）、`edit_file`（编辑文件）、`web_search`（联网搜索）。
- 每轮循环中，模型自行决定下一步是搜索资料、阅读参考文章、撰写文稿还是编辑修改。

## 预期行为：
Agent 自主完成「调研 -> 构思 -> 撰写 -> 修改」全流程，无需用户中途干预。最终在输出路径下生成完成的文稿。
```

## V0.2 描述：任务规划与状态管理

```Markdown
===v0.1版本新增以下描述===

## 任务规划机制：
- Agent 收到用户需求后，在进入循环之前，必须先制定一份结构化的任务计划。
- 任务计划以 markdown 文件的形式保存在输出路径下（`plan.md`），包含步骤清单和当前状态。
- 计划中每一步是一个 checkbox 项，格式如：`- [ ] 步骤描述`。完成的步骤标记为 `- [x]`。
- 计划还包含一个「当前状态」区域，标注当前执行到第几步、备注信息等。

## 状态管理机制：
- Agent 每完成一个步骤，必须先更新 plan.md（打勾 + 更新当前状态），再继续下一步。
- 当所有步骤都打勾后，Agent 做一次最终检查，确认文稿已写入输出路径，然后结束任务。

## 熔断机制：
- 设置最大循环轮次为 50 轮。超过 50 轮强制停止，输出当前已有成果。

## 预期效果：
通过强制任务规划和状态追踪，让 Agent 在长任务中始终保持「知道自己做到哪了」，减少跑偏、重复、遗漏的发生。
```

## V0.3 描述：上下文管理

```Markdown
===在 v0.2 的基础上，新增以下描述===

## 上下文压缩策略：
- 当 Agent 的消息历史（所有对话轮次的总 token 数）接近上下文窗口的 70% 时，系统自动触发压缩。
- 压缩方式：调用一个独立的 LLM 请求，将早期对话轮次（已完成步骤的工具调用细节）压缩为摘要，替换原始消息。
- 压缩后的摘要中保留：关键结论、决策理由、文件路径引用。丢弃：搜索结果原文、中间推理过程、已归档文件的完整内容。
- 被压缩的原始内容写入输出路径下的 `.archive/` 目录，Agent 需要时可以重新读取。

## Subagent 支持：
- 搜索环节支持派生子 Agent（Subagent）。主 Agent 发出搜索指令，Subagent 在独立的上下文中执行搜索、筛选，只返回结论摘要给主 Agent。
- 好处：10 条搜索 x 每条 3000 字的原始结果，压缩为 10 条 x 每条 50 字的摘要，主 Agent 上下文占用从 30000 字降到 500 字。

## 工作记录机制：
- Agent 每完成一个步骤，将该步骤的工作记录（做了什么、关键结论、生成了哪些文件）写入输出路径下的 `work_log.md`。
- 后续步骤需要回顾之前的结果时，从 `work_log` 读取，而不是依赖对话历史中的原始内容。

## 技能按需加载：
- 如果 Agent 内置了多种写作技能模板（如学术写作、公众号写作、商业文案），系统提示词中只放技能目录（名称 + 一句话描述）。
- 当模型判断需要某种技能时，通过工具调用加载该技能的完整说明，注入当前上下文。

## 预期效果：
通过压缩、分流、按需加载等策略，让 Agent 在有限的上下文窗口内完成长链路任务，不会因为信息撑爆窗口而中断。
```

## V0.4 描述：沙箱与权限管理

```Markdown
===在 v0.3 的基础上，新增以下需求：===

## 工作空间沙箱：
- Agent 的所有文件操作必须限制在用户指定的输出路径内。系统在每次执行文件操作前，自动将路径解析为绝对路径并校验是否在工作空间内，越界则拒绝执行并返回错误信息给 Agent。
- 工作空间即输出路径，Agent 启动时自动确认该路径存在且可写。

## 命令分层权限：
- 白名单命令（直接执行，无需用户确认）：`ls`、`cat`、`mkdir`、`grep`、`head`、`tail`、`wc`、`pwd`
- 需确认命令（执行前弹窗询问用户）：`curl`、`wget`（下载外部资源）、`rm`（删除文件）、`mv`（移动文件）
- 黑名单命令（永远拒绝）：`rm -rf /`、`chmod 777`、`sudo`、任何涉及系统目录的操作

## 路径逃逸防护：
- Agent 在多次目录跳转中可能拼接出 `../../` 这样的路径意外逃出工作空间。系统在每次文件操作前，将路径规范化（resolve）后再做校验。

## 联网内容管理：
- 联网下载的内容（如搜索结果、网页正文）必须保存到输出路径下的 `sources/` 子目录，不得写入其他位置。

## 预期效果：
通过沙箱和权限分层，确保 Agent 的活动范围可控，即使模型推理出错也不会造成破坏性操作。
```

## V0.5 描述：Hooks 自动化

```Markdown
===在 v0.4 的基础上，新增以下需求===

## Hooks 机制：
- 在 Agent 循环的关键节点，插入自动执行的脚本（Hooks），不经过模型推理，由程序直接执行。
- 需要实现以下 Hooks：

## 执行前 Hooks（工具调用之前触发）：
- 路径校验 Hook：对所有文件操作的路径参数做安全校验（解析绝对路径 -> 检查是否在工作空间内 -> 越界则拦截并返回错误）。
- JSON 格式校验 Hook：检查模型生成的工具调用参数格式是否正确（如缺少引号、括号不匹配等），可自动修复的就修复，修复不了的才回传给模型重新生成。

## 执行后 Hooks（工具调用之后触发）：
- 任务状态注入 Hook：每轮循环结束时，自动读取 plan.md 的最新内容，拼接到消息列表末尾。利用近因效应确保模型每轮都能看到「我做到哪了」。
- 工作日志 Hook：每次 `write_file` / `edit_file` 执行成功后，自动将文件变更记录追加到 `work_log.md`。
- 进度监控 Hook：每轮循环结束时，检查 plan.md 的最后更新时间。如果连续 3 轮未更新，向消息列表注入一条提醒：「你已经 3 轮没有更新任务计划了，请审视当前进度。」
- 上下文压缩 Hook：每轮循环结束时，检查消息总长度。超过上下文窗口的 70% 时，自动触发上下文压缩流程。

## 预期效果：
通过 Hooks 将机械性操作从模型的注意力中剥离出来，模型专注于写作本身，后台管家负责状态维护、安全检查和进度监控。
```

## V0.6 描述：记忆管理

```Markdown
===在 v0.5 的基础上，新增以下需求：===

## 记忆系统：
- 记忆提取：每次任务结束后，系统自动调用 LLM，从本次对话中提取值得长期记忆的信息，包括：用户偏好的写作风格、常写主题、被纠正过的写作习惯、常用输出路径等。提取结果以结构化文本存储。
- 首轮注入：每次新会话开始时，系统自动将用户记忆摘要注入到首轮上下文的系统提示词区域。Agent 在写作过程中应遵循这些偏好，但如果用户在本次对话中给出冲突指示，以本次为准。
- 记忆更新：每次任务结束后，新的提取结果与已有记忆合并（去重、更新、淘汰过时信息）。

## 跨会话检索：
- 当用户在新会话中提到「上次写的那篇 XX」「之前我们讨论过的 XX」等涉及历史会话的内容时，Agent 可通过关键词检索历史会话记录。
- 检索结果不是全量加载，而是只拉取与关键词相关的片段摘要，注入当前上下文。

## 预期效果：
Agent 从「每次见面都是陌生人」进化为「越用越懂你的写作助手」。用户无需每次重复自己的偏好，历史产出也可被复用和引用。
```

## V0.7 描述：错误恢复

```Markdown
===在 v0.6 的基础上，新增以下需求：===

## 错误恢复机制：

### 错误结构化处理：
- 工具调用失败时，不把原始错误日志直接丢给模型。系统自动将错误处理为结构化摘要，包含：失败的工具名、失败原因（超时/权限/格式等）、建议的下一步操作（重试/换策略/跳过）。
- 结构化错误信息比一堆 stack trace 对模型友好得多，模型看到后知道该怎么做。

### 失败计数与降级策略：
- 对每个工具的每次调用维护失败计数。
- 第 1 次失败：将结构化错误信息返回给模型，让它自行决定是否重试。
- 第 2 次失败：在错误信息中明确建议「换策略或跳过该步骤」。
- 第 3 次及以上失败：强制跳过该步骤，在 plan.md 中标记为「已跳过」并记录原因，继续执行后续步骤。

## 自动存档与回滚：
- 每次 write_file 或 edit_file 执行成功后，系统自动保存一份快照（如通过 git commit 或文件备份）。
- 如果后续步骤导致文稿损坏，Agent 或用户可以回滚到上一个正确版本。

## 预期效果：
通过结构化错误处理、渐进式降级和自动存档，确保 Agent 在面对工具调用失败时「小错不崩、大错可控」，不会因为一次失败就导致整个任务报废。
```

## 流程图文字节点

### 图 1：最小 Agent 闭环

1. 用户需求：写作主题、风格参考文章、输出路径。
2. Agent Loop：把需求、消息历史和工具列表交给模型。
3. LLM 推理：判断下一步该搜索、读文件、写作还是修改。
4. 工具调用：`bash` / `read_file` / `write_file` / `edit_file` / `web_search`。
5. 工具结果回灌：把执行结果追加回消息历史。
6. 循环判断：继续执行，直到模型给出最终交付。
7. 最终产物：在指定路径生成文稿，并返回交付说明。

### 图 2：任务规划与状态管理

1. 收到用户需求。
2. 生成 `plan.md`。
3. 将任务拆成 checkbox 清单。
4. 标记当前唯一 `in_progress`。
5. 执行当前步骤。
6. 完成后更新状态。
7. 每轮末尾重新注入计划。
8. 连续 3 轮未更新时触发提醒。
9. 所有关键步骤完成后进入最终检查。

### 图 3：上下文管理

1. 首轮组装：系统角色、工具说明、任务清单、环境信息。
2. 按需加载：技能目录常驻，技能全文按需注入。
3. 搜索分流：主 Agent 委派 Subagent 搜索。
4. Subagent 筛选并摘要结果。
5. 主 Agent 只接收结论摘要。
6. 工具结果增长到阈值。
7. 旧消息归档到 `.archive/`。
8. 活跃上下文只保留摘要、路径和关键决策。

### 图 4：沙箱与权限管理

1. Agent 发起工具调用。
2. 解析工具类型：文件读写、bash、联网搜索。
3. 路径标准化为绝对路径。
4. 校验是否在工作空间内。
5. 判断命令权限层级：白名单、需确认、黑名单。
6. `allow`：直接执行。
7. `ask`：请求用户确认。
8. `deny`：拒绝执行并把原因回灌给模型。
9. 模型选择安全替代方案。

### 图 5：Hooks 自动化

1. 用户输入进入 Agent Loop。
2. `PreToolUse`：参数格式校验、路径校验、权限校验。
3. 工具执行。
4. `PostToolUse`：格式化工具结果、摘要大结果、记录日志。
5. `PostWrite`：写入后记录 `work_log.md` 或保存快照。
6. 每轮结束：注入 `plan.md` 最新状态。
7. 每轮结束：检查是否需要上下文压缩。
8. 每轮结束：检查是否连续多轮未更新计划。
9. 模型继续专注写作任务本身。

### 图 6：记忆管理

1. 任务结束。
2. 记忆提取 Hook 扫描对话与产出。
3. 提取候选记忆：用户偏好、任务模式、纠正记录、常用路径。
4. 与已有记忆合并、去重、更新。
5. 新会话开始。
6. 首轮只注入记忆摘要或索引。
7. 用户提到历史内容时触发检索。
8. 只加载相关历史片段。
9. Agent 沿用偏好，但本轮明确指令优先。

### 图 7：错误恢复

1. 工具调用失败。
2. Hook 捕获原始错误。
3. 将错误改写为结构化摘要：工具名、原因、建议、失败次数。
4. 第 1 次失败：交给模型自行决定是否重试。
5. 第 2 次失败：建议换策略或跳过。
6. 第 3 次失败：强制跳过并更新 `plan.md`。
7. 写入类工具成功后自动保存快照。
8. 后续产物损坏时回滚到上一个正确版本。
9. 任务继续执行，避免一次错误拖垮全局。

### 图 8：七层迭代全景

1. V0.1 出厂配置：Agent Loop + Tools。
2. V0.2 任务规划与状态管理：TodoWrite + 状态追踪 + 熔断。
3. V0.3 上下文管理：上下文压缩 + Subagent + Skills 按需加载。
4. V0.4 沙箱与权限：路径沙箱 + 命令分层权限。
5. V0.5 Hooks 自动化：路径校验 + 状态注入 + 进度监控。
6. V0.6 记忆管理：记忆提取 + 跨会话检索。
7. V0.7 错误恢复：结构化错误处理 + 失败降级 + 自动存档。
8. 最终结果：从「能跑」进化为「可靠、可控、可恢复、可长期演进」。

## 总结：七层迭代全景

| 层级 | 主题 | 解决的问题 | 核心 Harness 组件 |
|---|---|---|---|
| V0.1 | 出厂配置 | 模型能「动起来」 | Agent Loop + Tools |
| V0.2 | 任务规划与状态管理 | Agent 知道自己在干嘛 | TodoWrite + 状态追踪 + 熔断 |
| V0.3 | 上下文管理 | 在有限空间里「无限」工作 | 上下文压缩 + Subagent + Skills 按需加载 |
| V0.4 | 沙箱与权限 | Agent 不会「越界」 | 路径沙箱 + 命令分层权限 |
| V0.5 | Hooks 自动化 | 机械操作不浪费模型注意力 | Hooks（路径校验 / 状态注入 / 进度监控） |
| V0.6 | 记忆管理 | Agent 越用越好 | 记忆提取 + 跨会话检索 |
| V0.7 | 错误恢复 | 小错不崩，大错可控 | 结构化错误处理 + 失败降级 + 自动存档 |

## Model + Harness = Agent 公式解释

> **Model + Harness = Agent**

我们用七层迭代，展示了「Harness」到底在做什么：

- **循环**让模型能行动。
- **任务规划**让模型不迷路。
- **上下文管理**让模型不遗忘。
- **沙箱**让模型不越界。
- **Hooks**让机械操作不消耗模型注意力。
- **记忆**让模型能成长。
- **错误恢复**让模型不崩溃。

每一层都不是「锦上添花」，而是在真实场景中必须解决的工程问题。跳过任何一层，Agent 在实际使用中都会暴露对应的缺陷，这就是 Harness 工程的意义。

## 附录：给产品经理的自检清单

如果你正在设计一个 Agent 产品，可以用这份清单逐项检查：

- [ ] **循环控制**：Agent 有明确的停止条件吗？最大轮次限制是多少？
- [ ] **任务规划**：Agent 能生成任务清单吗？清单会在每轮循环中被回顾吗？
- [ ] **状态管理**：Agent 怎么知道自己做到哪了？连续跑偏时有检测机制吗？
- [ ] **上下文窗口**：系统提示词占了多少 token？工具定义占了多少？给对话历史留了多少空间？
- [ ] **上下文压缩**：消息历史太长时怎么处理？压缩后关键信息丢了吗？
- [ ] **沙箱**：Agent 的文件操作有路径限制吗？能逃逸出工作空间吗？
- [ ] **权限管理**：哪些命令直接执行？哪些需要用户确认？哪些永远禁止？
- [ ] **Hooks**：哪些操作可以自动化？不依赖模型主动记得去做？
- [ ] **记忆**：用户的偏好怎么跨会话传递？历史会话怎么检索？
- [ ] **错误处理**：工具调用失败时怎么告诉模型？连续失败时怎么降级？
- [ ] **用户追加消息**：Agent 干活时用户发了新消息，怎么处理？中断还是排队？
